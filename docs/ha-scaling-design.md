# 高可用与高并发设计方案

> 目标：把当前"单进程、内存态、无观测"的信令服务，演进成一个**能讲清楚取舍、有实测数字**的分布式系统。
> 面向"找实习"的定位：**不是堆技术栈，而是证明你会在正确的地方做取舍。**

---

## 0. 先立结论：这个系统的瓶颈在哪

这是整个方案的地基。面试时如果只能记住一件事，记这个：

| 平面 | 单次通话成本 | 量级 | 是不是瓶颈 |
|---|---|---|---|
| **信令**（WebSocket 转发 SDP/ICE） | 一次性 ~10~20 KB，之后几乎为 0 | 1 万通电话/分钟 ≈ 20 Mbps 突发 | ❌ 完全不是 |
| **媒体**（P2P 直连） | 与你的服务器无关 | 0 | ❌ 不占你的资源 |
| **媒体**（TURN 中继） | **每个通话双向 ~3~5 Mbps 持续占用** | 1 Gbps 网卡 ≈ **200~300 路中继** | ✅ **这才是墙** |

推论：

1. **信令服务的"高并发"不是吞吐问题，是"连接数 + 状态一致性 + 故障语义"问题。**
   一台 muduo 单机轻松扛 10 万空闲 WebSocket 连接（每连接约 2~5 KB，10 万连接 ≈ 200~500 MB）。所以简历上写"信令支持 10 万并发"没有含金量，写"节点宕机后通话 3 秒内自动恢复"才有。
2. **真正的水平扩展发生在 TURN 集群上**，而它受限于**带宽（钱）**而不是 CPU。
3. 因此正确的演进顺序是：**单机健壮性 → 无状态化 + 故障恢复 → 媒体面扩展**。
   一上来就上 Kafka/K8s 是典型的简历造假式设计，面试官一问细节就崩。

## 1. 现状盘点（对着现有代码说问题）

这些是真实存在的、可以拿去当"优化前"基线的点：

| 位置 | 问题 | 影响 |
|---|---|---|
| `g_rooms` / `g_rooms_mutex` | 房间状态是**进程内存**，全局单锁 | 无法多实例；多核下锁竞争；重启即丢 |
| `g_ws_clients` / `g_bye_processed` / `g_pong_pending` | 又是 3 个全局 map + 3 把锁 | 状态分散，锁序靠人工维护，易错 |
| 转发/查找对端 | **线性扫描所有房间**找 conn 所在房间 | O(房间数)，房间多了退化 |
| `main()` | 没有信号处理 | `kill` 直接断连，无法优雅下线 → 不能不停机发布 |
| `onMessage` → `conn->send()` | 无输出水位线控制 | 慢客户端/恶意客户端会撑爆内存 |
| 只有日志 | 无 `/healthz`、无 `/metrics` | 无法接入监控、无法做 SLO、排障靠 grep |
| `loadTurnConfig` | ICE 配置在启动时读一次 | 改配置要重启；多实例配置不一致 |
| 无鉴权 / 无限流 | ✅ **鉴权已补**（WS 首消息 `auth`，HS256 JWT，5 秒超时）；仍缺 **WS 侧限流** | 剩余风险：可被刷连接数、刷房间占用内存 |

> 注意：**这些不是"必须全部修"，而是"你可以逐条报出前后对比数字"的素材。**
> 面试里"我把全局锁拆成 64 个分片锁，1 万房间下 p99 转发延迟从 X ms 降到 Y ms"远比"我用了 Redis 集群"有说服力。

## 2. 目标与非目标

### SLO（要写进 README，并且要能实测）

| 指标 | 目标 | 怎么测 |
|---|---|---|
| 信令连接容量（单节点） | ≥ 50,000 空闲连接 | k6 压测，看 RSS 与 fd |
| 单房间入房延迟 | p99 < 50 ms | k6 记录 `join_room` → `joined` |
| 信令转发延迟 | p99 < 20 ms（同机房） | offer/answer/ice 往返 |
| **节点故障恢复时间（RTO）** | **< 5 s 恢复通话** | `kill -9` 一个节点，测"重新出画面"耗时 |
| 发布可用性 | 滚动重启期间通话不中断 | 压测流量下滚动重启 |
| 单节点故障影响面 | 只影响该节点上的通话，其余不受影响 | 故障演练 |

### 非目标（刻意不做，并在文档里写明理由）

- 不做跨机房双活：通话是分钟级的短会话，跨机房同步的收益远小于成本。
- 不做房间状态的强一致持久化：房间是**易失状态**，丢了就让客户端重连重建。
- 不做媒体服务器的自研 SFU：那是另一个项目。

## 3. 目标架构

```
                        ┌──────────── 客户端 ────────────┐
                        │  ws://host/ws?room=ABC&rt=...  │
                        └───────────────┬────────────────┘
                                        │ WSS
                              ┌─────────▼──────────┐
                              │  SLB / nginx ×2    │  ← keepalived VIP / 云 SLB
                              │  健康检查 + 负载均衡 │
                              └───┬────────────┬───┘
                    ┌─────────────▼──┐   ┌─────▼──────────┐
                    │ signaling-1    │   │ signaling-2    │   ← 无状态，可随意增减
                    │ 本地连接表      │   │ 本地连接表      │
                    └───┬────────┬───┘   └─────┬──────────┘
                        │        │             │
          presence/状态 │        └──── 信令总线 ─┘      ← Redis Pub/Sub 或 NATS
                        ▼          (按 roomId 路由)
                 ┌──────────────┐
                 │ Redis (主从)  │  room:{id} → {slot, node, connId, ts}  TTL 续租
                 └──────────────┘
                        │
        ┌───────────────┴────────────────┐
        │  TURN 集群 coturn-1..N          │  ← 真正需要横向扩展的地方（带宽）
        │  ICE 服务器列表随机/按地域下发    │
        └────────────────────────────────┘
```

**核心思想：把"连接"和"房间"解耦。**

- 连接是有状态的、绑定在某个节点的（WebSocket 天然如此，不可迁移）。
- 房间是逻辑概念，状态放 Redis，消息经总线按 roomId 路由。
- 于是：**任何节点都能服务任何客户端**，节点增减不影响正确性。

## 4. 关键设计决策

### 4.1 房间状态放哪？——不要用一致性哈希粘性路由

**方案 A：客户端把 roomId 放进 URL，nginx 按 roomId 一致性哈希到固定节点。**
- 优点：实现最省事，不用引入 Redis。
- **致命缺陷**：扩容时（加一个节点）一致性哈希会重映射一部分房间，新连接落到新节点，而房间里的老对端还在老节点上 → **两端在不同进程里，配不上对**。
  也就是说：**它恰好在你最需要扩容的那一刻坏掉。**
- 结论：只能作为"临时过渡"，不能作为目标态。

**方案 B：节点不存房间的权威状态，状态放 Redis，消息走总线。**
- 任意节点可服务任意客户端；节点宕机只影响它上面的连接，客户端重连到别的节点即可。
- 代价：多一跳总线（同机房 <1 ms），多一个故障域（Redis）。
- 结论：**采用 B。** 这也是 LiveKit / Janus 这类系统实际的做法。

### 4.2 消息路由——广播过滤 vs 主题订阅

| 方案 | 机制 | 适用规模 | 取舍 |
|---|---|---|---|
| Redis Pub/Sub 分片广播 | 64 个 shard，`shard = hash(roomId) % 64`，每个节点订阅全部 shard，收到后查本地连接表决定是否转发 | ≤ 20 节点 | 简单、运维成本低；消息会广播给所有节点（浪费，但信令消息本来就少） |
| NATS 主题订阅 | 主题 `signaling.room.{roomId}`，NATS 只投递给有订阅的节点 | 任意 | 路由更精准，但多一个中间件 |

**建议**：先用 Redis 分片广播（信令量级下"广播浪费"根本不算事），把这作为设计的**已知取舍**写进文档——面试官会认可这种"知道它不完美但算过账"的判断。

```
发布：PUBLISH signaling:{hash(roomId)%64}  {"room":"ABC","to":"slot2","msg":{...}}
订阅：每个节点 SUBSCRIBE signaling:0..63
      收到 → 查本地 roomId→conn 表 → 命中则写到对应连接，未命中直接丢弃
```

### 4.3 会话续租（Seat Reclaim Token）—— 高可用的关键

节点宕机时，房间在 Redis 里的两个座位需要能被"接手"。设计：

1. 入房成功（`joined`）时下发 `reconnectToken`：
   `token = base64(HMAC-SHA256(nodeSecret, roomId + ":" + slot + ":" + issuedAt))`
   （或者直接存一个随机 UUID 到 Redis 的座位记录里）
2. 客户端把 token 存 `sessionStorage`。
3. 重连时带 `wss://host/ws?room=ABC&rt=<token>`。
4. 新节点用同样的 nodeSecret 验签，再查 Redis：
   - 座位记录的 `node` 还是自己 / 已过期（TTL 到）→ **直接接管该座位**；
   - 座位活跃且在别的节点 → 说明是重复登录，按策略拒绝或顶掉旧连接。
5. `nodeSecret` 通过**配置文件/环境变量下发**给所有节点（不引入 KMS，够用）。

> 这一步让"节点宕机 → 客户端重连 → 通话自动恢复"从"靠运气"变成"有协议保证"，
> 并且 RTO 变成**可测量、可写进简历的数字**。客户端已有的指数退避重连逻辑直接复用。

对比：如果做"服务端状态复制"（每个房间的状态实时同步到其它节点），成本高得多，而且对一个分钟级会话完全是过度设计。**这里选择"客户端驱动的重建"，并把这个取舍讲清楚，就是一个加分项。**

### 4.4 优雅下线与零停机发布

当前 `main()` 没有任何信号处理，`kill` 即断连。设计：

```
收到 SIGTERM：
  1. 置 draining 标志 → 新的 join_room 直接回 error{code:"server_draining"}
     （客户端收到后换节点重试，而不是傻等）
  2. 向本节点所有在通话的连接发 bye{reason:"server_shutdown"}
  3. 发送 WebSocket Close(1001 Going Away)
  4. 等待最多 3 s flush 输出缓冲，然后退出
客户端：
  收到 1001 → 走已有的指数退避重连 → 带 reconnectToken 到新节点 → 恢复通话
```

由此得到 **"滚动发布期间通话不中断"** 的能力，并且可以录一个演示：压测流量跑着，逐个重启节点，客户端只是在状态栏闪一下"正在重新连接"，画面恢复。**这个演示视频比任何架构图都有用。**

### 4.5 分布式下的连接生命周期

沿用已有的 ping/pong 心跳，但语义升级为**分布式租约**：

- 节点每 30 s ping，并 `EXPIRE room:{id} 60` 续租它占用的座位。
- 节点 `kill -9` 后无人续租 → Redis 里的座位记录 60 s 内过期 → 房间可被重新使用。
  （这就是现在单机版 `g_pong_pending` 两轮回收的分布式对应物。）
- 副作用与取舍：**最坏 60 s 的"幽灵座位"窗口**。为了缩短，可以把 TTL 降到 15 s + 心跳 5 s。
  这个"TTL/心跳间隔 vs 误判率 vs 幽灵窗口"的三角权衡，是面试里很好讲的一个点。

### 4.6 背压与限流（现在完全没有，改动小、收益大）

```cpp
// muduo 提供的水位线回调
conn->setHighWaterMarkCallback([](const TcpConnectionPtr& c, size_t len) {
    // 1MB：进入降级模式，丢弃 ICE 候选（它是可再生的，丢了会自动补）
    // 4MB：判定为慢/恶意客户端，直接 forceClose
}, 1 << 20);
conn->setWriteCompleteCallback([](const TcpConnectionPtr& c) {
    // 退出降级模式
});
```

限流（令牌桶）：
- **每连接**消息速率：如 200 msg/s（正常信令远低于此，SDP 也就几条）。
- **每 IP** 建连速率：如 20 次/分钟（防刷连接）。
- **每房间** join 尝试速率：防房间号爆破。

> 知识点：为什么 ICE 候选可以丢——因为它本来就是"有更好、没有也能连"的增量信息，丢了浏览器会用已收集到的候选继续尝试。**能讲清楚"哪种消息可以丢"，说明你真的理解协议而不只是会调 API。**

### 4.7 可观测性（性价比最高的一块）

复用现有的 HTTP 处理分支（`parseHttpPath`），加两个路由：

| 路由 | 内容 | 用途 |
|---|---|---|
| `GET /healthz` | `200 ok` | 存活探针（liveness） |
| `GET /readyz` | Redis 可达 + 未 draining → `200`，否则 `503` | 就绪探针（readiness），SLB 摘流量的依据 |
| `GET /metrics` | Prometheus 文本格式 | 监控与压测出图 |

指标清单（都是几行代码的计数器）：

```
signaling_connections_active              gauge    当前连接数
signaling_rooms_active                    gauge    当前房间数
signaling_join_total{result="ok|full|draining"}   counter
signaling_relay_total{type="offer|answer|ice|..."}  counter
signaling_relay_latency_seconds           histogram 转发延迟
signaling_heartbeat_evicted_total         counter    心跳回收数
signaling_dropped_total{reason="backpressure|ratelimit"}  counter
process_resident_memory_bytes / process_open_fds     gauge
```

> `/readyz` + SLB 健康检查是"高可用"最实在的一环：**摘流量要快，摘完才重启**，否则重启就是一次小事故。

### 4.8 单机内的并发模型（不需要分布式也能做，且有数字可测）

| 现状 | 优化 | 预期收益（需实测） |
|---|---|---|
| 5 个全局 map + 5 把锁 | 连接级状态归 IO 线程私有；房间表按 roomId 哈希成 64 个分片，各带一把锁 | 多核下锁竞争大幅下降 |
| 线性扫描所有房间找 conn | 维护 `conn → roomId` 索引（`unordered_map`） | 转发从 O(房间数) 降到 O(1) |
| 日志 `fwrite` + `fflush(stdout)` 每行 | 已有 AsyncLogging，但 stdout 仍是同步写 | 去掉 stdout 刷盘或改批量 |
| `setThreadNum(4)` | 按 CPU 核数配置，并做 Reactor 绑核验证 | 吞吐随核数近线性 |

**这部分是"最快能出数字"的**：改完写个压测脚本，直接得到"10 万连接下单节点 CPU 40%、p99 转发 8 ms"这类可写进简历的句子。

### 4.9 配置与多实例一致性

- 端口、线程数、Redis 地址、`nodeSecret`、ICE 配置路径 → 全部走环境变量 / 配置文件。
- ICE 配置改成**定期热加载**（如 30 s 检查 mtime），避免"改 TURN 要重启所有节点"。
- 更彻底：ICE 凭据不落盘，由信令节点按 4.3 的思路**在每次 `start_call` 时动态生成**（REST 临时凭据）。

## 5. 媒体面的高并发与高可用（真正的墙）

信令做完分布式之后，你会撞上这一层。

### 5.1 TURN 集群

coturn **不支持集群**，做法是"多实例 + 客户端择优"：

```
iceServers: [
  { urls: "turn:turn-a.example.com:3478?transport=udp", username, credential },
  { urls: "turn:turn-b.example.com:3478?transport=udp", username, credential },
  { urls: "turn:turn-a.example.com:3478?transport=tcp", username, credential }  // UDP 被封时兜底
]
```

- 多实例各自独立，客户端 ICE 会依次尝试。
- 前面挂 L4（DNS 轮询 / LVS / 云 SLB UDP）做流量分摊。
- **单实例带宽上限 = 网卡带宽**，1 Gbps ≈ 200~300 路中继，这是硬上限，必须做**按用户的带宽/会话配额**（`user-quota`、`total-quota`、`max-bps`），否则一个用户就能打满。
- 高可用：健康检查 + 摘除故障实例；客户端要能容忍某个 TURN 不可达（多给几个地址）。

### 5.2 容量核算（把这张表背下来，面试能用）

```
中继单路成本 = 上行 bitrate + 下行 bitrate
             ≈ 1.5 Mbps + 1.5 Mbps = 3 Mbps（720p 典型值）

1 Gbps ≈ 1000 / 3 ≈ 330 路中继（理论上限，实际留 30% 余量 → ~230 路）

P2P 直连成功率（国内经验值，需自测）：
  同城家宽         ~85%
  4G/5G            ~60~70%（运营商级 NAT 多）
  → 也就是说 100 路通话大约 15~40 路要走中继
```

**结论**：真正决定"能撑多少路通话"的是**中继带宽预算**，不是信令节点数。
一个能说出这句话的候选人，和一个只会说"我用了 Redis 集群"的候选人，差距就在这里。

### 5.3 可选进阶：SFU 与群聊

一对一之外真正有意思的扩展是**多人通话**，这条路会把你带到 SFU（mediasoup / LiveKit / Janus）：

- 从 P2P Mesh（N 人 N² 条流，>4 人就废）切到 SFU（每人 1 上 1 下）。
- 变成 **CPU 密集**：单 vCPU 大约能转发 20~50 路 720p（必须自己实测）。
- 这时"高并发"终于变成你熟悉的"加机器 + 负载均衡 + 房间调度到特定 SFU"，
  并且可以引出**调度器（room → SFU 分配）**这个很漂亮的分布式子问题。

**但这是另一个项目的工作量。** 建议：先做完信令的分布式与可观测，把 SFU 作为"下一步规划"写在文档里——面试被问到"如果要做群聊怎么办"时，能讲清楚上面这几句就足够。

## 6. 压测与故障演练（这是把方案变成"数字"的唯一途径）

### 6.1 工具

| 目标 | 工具 | 说明 |
|---|---|---|
| 信令连接数与延迟 | **k6**（内置 `k6/ws`） | 一台机器可模拟数千连接，输出 p95/p99 |
| 房间级场景（入房→配对→交换 SDP→挂断） | 自写 Node/Go 客户端 | 需要实现最小信令协议，100 行以内 |
| 真实端到端（含媒体） | Puppeteer + `--use-fake-device-for-media-stream` | 假摄像头，不依赖硬件 |
| TURN 中继压力 | `turnutils_uclient` | coturn 自带 |
| 系统指标 | `node_exporter` + Prometheus + Grafana | 出图 |

### 6.2 必做的四张表（直接进 README，面试时甩出来）

1. **容量曲线**：连接数 1k/5k/10k/50k → CPU%、RSS、fd、p99 入房延迟。
2. **锁优化前后对比**：全局锁 vs 64 分片锁，在 1 万房间下的转发 p99。
3. **故障演练**：`kill -9` 一个节点 → 受影响通话数、重连成功率、**RTO 分布（p50/p99）**。
4. **滚动发布**：压测流量下依次重启 3 个节点 → 通话中断率、用户可感知的卡顿时长。

> 第 3、4 张表才是"高可用"的证据。没有故障演练的"高可用"只是 PPT。

## 7. 分阶段路线图

| 阶段 | 内容 | 工作量 | 产出物（可写进简历） |
|---|---|---|---|
| **P0 单机健壮性** | `/healthz` `/readyz` `/metrics`；SIGTERM 优雅下线；背压水位线；每连接/每IP 限流；`conn→roomId` 索引；房间表分片锁 | **2~4 天** | "信令服务接入 Prometheus 监控与就绪探针；全局锁改 64 分片锁，1 万房间下转发 p99 从 __ ms 降到 __ ms；支持优雅下线，滚动发布通话不中断" |

## 8. 面试怎么讲

### 8.1 这套设计能让你接住的问题

| 面试官问 | 你要答的要点 |
|---|---|
| 你这个项目哪儿有高并发？ | 先纠正前提："信令的量级很小，1 万通电话的信令突发只有 ~20 Mbps；真正的瓶颈是中继带宽，1 Gbps 只能撑 200~300 路。" 然后讲连接数、状态一致性、故障语义。 |
| 为什么不用一致性哈希做粘性路由？ | 扩容时重映射会把同一房间的两端分到不同节点，**恰好在扩容时坏掉**。所以选择"无状态 + 外部状态 + 总线路由"。 |
| 房间状态为什么不用 etcd/MySQL 保证强一致？ | 通话是分钟级易失会话，强一致的收益 < 成本；丢了让客户端重连重建即可。**"知道什么不需要强一致"是分布式的基本功。** |
| 节点宕机在途消息怎么办？ | 允许丢。信令消息中 `ice` 可再生、`offer/answer` 可由重连后的重协商补上；真正的兜底是客户端带 token 重建会话。 |
| 怎么做不停机发布？ | SIGTERM → draining → 拒绝新入房（`server_draining`）→ 老连接发 `bye` + `Close(1001)` → 客户端换节点重连接管座位 → SLB 就绪探针摘流量。 |
| 心跳 TTL 设多长？ | 三角权衡：TTL 短 → 误判多（网络抖动就掉线）；TTL 长 → 幽灵座位窗口长（房间被占着进不去）。给出你选的参数和实测依据。 |
| 慢客户端怎么办？ | muduo 高水位回调：1 MB 进入降级模式丢 ICE 候选，4 MB 直接断开。 |
| 怎么证明你说的都真的？ | **甩压测表和故障演练表。** |

### 8.3 诚实提醒（这条可能比上面所有内容都重要）

- **这个项目最大的加分项其实是 WebRTC 本身的深度**：perfect negotiation 的 polite/impolite 语义、ICE restart、DTLS-SRTP 的信任模型、"未开启设备"与"已关闭"的区分（`track.enabled` vs 无 track）、为什么 `bye` 要保留房间。这些细节能证明你真的读懂了协议，而不是抄了个 demo。**面试里讲得清这些，比堆一个分布式方案更值钱。**
- **规模不匹配是真会被问穿的。** 一个"一对一通话"的项目硬套 Kafka + K8s + 多机房，面试官第一反应是"这不是你做的"。**方案里主动写"非目标"和"刻意不做"，反而显得成熟。**
- 后端实习笔试/一面占比很大的是 OS、网络、数据结构、数据库。这个项目是二面/三面的素材，不要为了它荒废基础。

## 9. 明确不要做的事

| 不要做 | 为什么 |
|---|---|
| 上 Kafka / RocketMQ 做信令总线 | 信令消息量级下，Redis Pub/Sub 甚至进程内队列都够；用 MQ 是杀鸡用牛刀，且会被追问"为什么不用更轻的" |
| 上 K8s / Service Mesh | 3 个节点的服务不需要编排系统；真上了也讲不出解决了什么具体问题 |
| 把房间状态写进 MySQL 并做事务 | 易失状态做持久化 + 强一致，纯属自找麻烦 |
| 为了"分布式"把 C++ 换成 Go/Java | 语言不是难点，换语言的收益是负的（你要重新踩 muduo 已解决的坑） |
| 写"支持百万并发"却没实测 | 面试官只要问一句"怎么压出来的"就结束了 |
| 无脑加缓存 | 信令路径上没有可缓存的热点数据，加缓存是纯粹的复杂度 |

## 10. 风险与返工点

| 风险 | 说明 | 缓解 |
|---|---|---|
| Redis 成为单点 | presence + 总线都依赖它 | Redis 主从 + Sentinel；节点侧做"Redis 不可用 → 降级为单机模式（房间只在本地，拒绝新节点加入）" |
| 广播模型的总线放大 | 每节点订阅全部 shard | 节点数 >20 时改为按 shard 分订阅，或换 NATS 主题路由 |
| `nodeSecret` 泄露 | 可伪造 token 抢座位 | 密钥走环境变量，定期轮换；token 带短 TTL |
| 故障演练环境 | 需要在云上开多台机器 | 本地用 docker-compose 起 3 个节点 + Redis 就能做，够用 |
| 过度投入 | 把时间全花在 P1/P2，耽误八股和算法 | 严格按 P0 → P1 顺序，每阶段做完就固化数字、更新 README |
