# 多人通话 / 直播场景设计方案（Mesh → SFU）

> 承接 [`ha-scaling-design.md`](ha-scaling-design.md)。那份文档里的信令高可用方案**在这里依然成立**，
> 而且会变得更重要——因为多人场景把真正的重活从"转发消息"变成了"转发媒体"。
>
> 一句话结论：**一对一改成多人，瓶颈从"带宽"变成"CPU + 带宽双约束"，你必须引入 SFU，
> 并且第一次真正需要"把有状态的房间调度到某台机器上"这个分布式问题。**

---

## 0. 先做拓扑选择：Mesh 为什么必然死

| 拓扑 | 上行占用（每个客户端） | 服务器开销 | 适用人数 | 结论 |
|---|---|---|---|---|
| **Mesh（全互联）** | (N-1) × 1.5 Mbps | 0（走 P2P） | ≤ 4 | ❌ 你现在的一对一方案直接推广到这里就死了 |
| **MCU（服务器混流）** | 1 × 1.5 Mbps | 解码 + 混流 + 编码，CPU 极高 | 任意 | ❌ 除非做录制/直播导播，否则不划算，且失去每人独立布局 |
| **SFU（转发）** | **1 × 1.5 Mbps** | 纯 RTP 转发，不解码 | 数人到数千 | ✅ **采用** |

算一下 Mesh 的死法（720p @1.5 Mbps）：

```
N = 4   → 上行 4.5 Mbps   ← 家用宽带开始吃力
N = 6   → 上行 7.5 Mbps   ← 大多数手机/家宽的上行极限
N = 10  → 上行 13.5 Mbps  ← 不可能
房间总流量 = N × (N-1) × 1.5 Mbps = O(N²)
```

SFU 的关键性质：

- 每个客户端**只推 1 路上行**，下行是"SFU 转发过来的若干路"。
- SFU 的出口带宽是 O(N × k)，`k` = 实际转发给这个接收者的流数——**而 k 是你可以控制的**（见 §4.5），这是整个方案的性能旋钮。
- 顺带一个大收益：**客户端复杂度暴降**。从"跟 N-1 个对端各建一条 PeerConnection"变成"只跟 SFU 建一条"。
  你的 `initiator/responder`、perfect negotiation、ICE restart 这些逻辑全部保留，只是协商对象从"对端浏览器"变成了"SFU"。

## 1. 关键洞察：「自由开关视频」这个需求本身，就是你最大的扩容杠杆

这是这份方案里最重要的判断，面试时一定要讲：

**同一个房间，两种流量模式差一个数量级。**

| 模式 | 典型形态 | SFU 出口 | 量级（N=100） |
|---|---|---|---|
| **会议模式** | 大多数人都开视频，互相能看见 | 每个接收者订阅多路 → **O(N²)** | 100×99×1.5 Mbps ≈ **14.8 Gbps**（必须靠 §4.5 压下来） |
| **广播模式** | 少数人开视频（主讲），其他人关视频只听 | 1 路源 × N 个接收者 → **O(N)** | 1×100×1.5 Mbps ≈ **150 Mbps** |

也就是说：**"大家自由选择是否打开视频"如果实现得好（默认关、按需订阅、只转发可见的），
一个 100 人房间的实际出口可能只有理论最坏值的 5%~10%。**

设计上要把这个杠杆显式化：

1. **默认不订阅视频**：进房先只订阅音频 + 花名册，视频按"可见性"订阅（§4.5）。
2. **观众侧关视频 = 零成本**：不推流的人不占任何上行，也不产生任何转发。
3. **主播侧关视频 = 一次 `producer.pause()`**：注意这里有个坑——`track.enabled=false` 只是发黑帧，
   **带宽照样在烧**；正确做法是让 SFU 侧 `pause` producer（见 §4.8 与 §10 的领域模型衔接）。

> 这正好接上你 `CONTEXT.md` 里"关闭摄像头 ≠ 未开启摄像头"的那套领域模型——多人场景下它价值更大，
> 因为"已关闭"必须被实现成"服务端停止转发"，否则 100 人房间里每个人关掉视频都在偷偷烧你的带宽。

## 2. 目标架构：信令面彻底无状态，有状态全部赶到 SFU

```
                      ┌──────────────── 客户端 ────────────────┐
                      │ 1) 信令 WSS → signaling 集群（无状态）  │
                      │ 2) 媒体 UDP/TCP → 被分配的 SFU 节点      │
                      └───────┬───────────────────────┬─────────┘
                              │                       │
                    ┌─────────▼──────────┐            │
                    │  signaling-1..N    │            │
                    │  无状态：           │            │
                    │  · 鉴权/签发 token  │            │
                    │  · 房间→SFU 调度    │            │
                    │  · 花名册/在线状态   │            │
                    └───┬────────────┬───┘            │
                        │            │                │
              ┌─────────▼──┐   ┌─────▼──────────┐     │
              │ Redis      │   │ SFU 调度器      │     │
              │ room→sfu   │   │ (weighted least │     │
              │ presence   │   │  load / spread) │     │
              └────────────┘   └─────┬──────────┘     │
                                     │ 心跳+负载上报   │
                    ┌────────────────▼────────────────▼──────┐
                    │  SFU 集群（有状态、CPU 密集、房间粘性）  │
                    │  sfu-1 (worker×cores)  sfu-2  sfu-3 …  │
                    │  Router(房间) → Transport → Producer/  │
                    │  Consumer（纯 RTP 转发，不解码）        │
                    └────────────────────────────────────────┘
                                     │
                          TURN（仅用于 UDP 被封的客户端）
```

三条设计主线：

1. **信令面变成纯无状态**：它不再"拥有"房间，只负责鉴权、调度决策、花名册查询。
   这反而让第一份文档里的无状态化设计**变得更容易做对**。
2. **媒体面是有状态的**：一个房间的 `Router` 必须固定在**同一个 SFU 进程**里（媒体流不能跨节点零成本搬）。
   于是"房间 → 哪个 SFU"成了一个新的、真正的分布式调度问题。
3. **两条链路分开部署、分开扩容**：信令按连接数扩容，SFU 按 CPU/带宽扩容。

## 3. SFU 选型：不要自己写

自己写 SFU 意味着实现 RTP/RTCP、NACK/RTX 重传、PLI/FIR 关键帧、TWCC/REMB 带宽估计、
simulcast 层切换、拥塞控制、DTLS/SRTP 终结……这是**另一个数月级的项目**，而且做出来也打不过成熟的。

| 方案 | 语言 | 适合你吗 | 说明 |
|---|---|---|---|
| **mediasoup** | C++ 核心 + Node 绑定 | ✅ **最推荐** | 和你的 C++ 技术栈衔接最自然；低层、可控，能讲清楚每个概念；只做 SFU，调度/信令要自己写——**这恰好是你想展示的部分** |
| LiveKit | Go | ✅ 备选 | 开箱即用（房间、JWT、webhook、录制都有），能更快出成果，但你要展示的"调度/HA"被它内置了，可讲的东西变少 |
| Janus | C | ⚠️ | 插件化，学习曲线陡，文档偏老 |
| ion-sfu / Pion | Go | ⚠️ | 轻量，适合自己拼装 |

**推荐组合**：保留你现有的 **C++/muduo 信令服务**（改造成无状态 + 调度器），
媒体面用 **mediasoup 的 worker 池**。这样你的简历故事是连贯的：
"我写的是信令与调度层，媒体转发用 mediasoup"——比"我调了 LiveKit 的 API"有内容得多。

## 4. 关键设计决策

### 4.1 房间 → SFU 调度器（这是你要展示的核心）

```
分配一个房间时：
  1. 从 Redis 读活跃 SFU 列表（每个节点 5s 心跳续租 TTL）
  2. 读每个节点的负载快照：cpu%、已承载房间数、已转发流数、出口带宽 Mbps
  3. 按加权最小负载选一个节点（权重：CPU 0.5 / 出口带宽 0.4 / 房间数 0.1，数值需实测调）
  4. 写 room:{roomId} → {sfuNode, routerId, createdAt}，TTL 续租
  5. 返回给客户端：{sfuUrl, roomToken}
```

**两个必须讲清楚的取舍：**

| 策略 | 效果 | 风险 |
|---|---|---|
| **Packing（尽量塞满）** | 省机器，跨节点级联少 | 一个节点挂掉影响房间多（爆炸半径大） |
| **Spread（尽量分散）** | 爆炸半径小，符合高可用 | 机器利用率低，成本高 |

→ **选 Spread，并设置 70% 的水位线**：超过就不接新房间（**宁可拒绝新房间，也不要让在线的房间集体劣化**）。
这个"过载时拒绝 vs 降级"的取舍是很好的面试题，你要能说出为什么选拒绝。

调度器本身的高可用：**做成无状态的多个实例，决策结果写 Redis 用 CAS 保证幂等**，
绝不能做成单点决策进程。

### 4.2 接入流程与 Token（复用第一份文档的 HMAC 思路）

```
客户端                signaling(无状态)              SFU
  │  join_room{roomId}      │                        │
  ├────────────────────────▶│                        │
  │                         │ 查 Redis：房间是否已分配 SFU
  │                         │ 未分配 → 问调度器 → 分配
  │                         │ 已分配 → 直接复用（幂等）
  │  joined{                │                        │
  │    selfId, peers[],     │                        │
  │    sfuUrl, roomToken}   │                        │
  │◀────────────────────────┤                        │
  │  WebSocket/WHEP 连到 SFU，带 roomToken            │
  ├─────────────────────────────────────────────────▶│
  │                         │        SFU 校验 token 签名（共享密钥）
  │                         │        → createRouter/Transport
```

- `roomToken` = JWT/HMAC，载荷 `{roomId, peerId, role, canPublish, exp}`，用集群共享密钥签名。
  **密钥只下发给节点和 SFU，永不出现在客户端代码里。**
- 好处：SFU 不需要回调信令服务就能独立鉴权（避免每次加入都同步 RPC），且 token 能自动过期。
- 这一套可以和第一份文档的 `reconnectToken` 合并成同一个 token 体系。

### 4.3 信令协议改造

现有协议是为一对一量身定做的（`initiator`/`responder`/`bye`），多人要重设计成**面向房间事件**：

**客户端 → 服务端**

| type | 载荷 | 说明 |
|---|---|---|
| `join_room` | `{roomId, displayName}` | 取 token + 花名册 + SFU 地址 |
| `leave_room` | `{}` | 与 `bye` 区分：人真的走了（`bye` 只结束通话） |
| `publish` | `{kind:"audio"\|"video", encodings}` | 开始推流（需权限） |
| `unpublish` | `{trackId}` | 停止推流 |
| `producer_pause/resume` | `{trackId}` | **关/开摄像头（服务端停转发，省带宽）** |
| `subscribe` | `{peerId, kind, preferredLayer}` | 订阅某人的流 |
| `unsubscribe` | `{peerId, kind}` | 取消订阅（tile 不可见时） |
| `set_preferred_layers` | `{peerId, spatial, temporal}` | 按 tile 大小/带宽切层 |
| `offer/answer/ice` | `{data}` | 与 SFU 的协商 |
| `bye` | `{}` | 结束通话并离开房间（当前一对一语义；多人化时要拆开，见 §4.3 末尾） |

**服务端 → 客户端**

| type | 载荷 | 说明 |
|---|---|---|
| `joined` | `{selfId, peers[], sfuUrl, roomToken, policy}` | 含房间策略（谁能发布） |
| `peer_joined` / `peer_left` | `{peerId, displayName}` | 花名册增量 |
| `peer_track` | `{peerId, kind, state:"added\|removed\|paused\|resumed"}` | **多人版的 `video_mute`**，驱动"对方已关闭摄像头"占位 |
| `active_speaker` | `{peerId, level}` | 服务端从 RTP 头扩展 `ssrc-audio-level` 判定 |
| `offer/answer/ice` | `{data}` | SFU 侧协商 |
| `error` | `{code, message}` | `room_full` / `no_capacity` / `publish_denied` |

> 注意 `bye` 与 `leave_room` 的区分——当前一对一版本里**挂断就等于离开房间**（房间是持久的，不靠"人还在里面"存活）。
> 到了多人场景，这个语义要再拆开：某人只是结束自己的通话，不该把整个房间的人赶走。届时应恢复
> `leave_room` 作为独立消息，并让 `bye` 只影响本端媒体。这是多人化时**必须回改**的一处。

### 4.4 发布权限必须在服务端

"大家自由选择是否打开视频"听起来是客户端自由，但**直播场景下这句话是危险的**：
如果人人可推流，一个房间 100 人全开视频就是上面那个 14.8 Gbps 的最坏情况。

所以房间要有 **policy**：

```
policy = {
  canPublish: "all" | "role" | "invite",   // 会议=all，直播=role
  maxPublishers: 9,                        // 同时最多几路视频（硬约束）
  maxVideoLayer: "h720",                   // 单人最高分辨率
  maxBitratePerPeer: 1500000,
  defaultSubscribe: ["audio"]              // 默认只订阅音频
}
```

服务端在 `publish` / `producer_pause` 时**强制校验**，前端只是展示。这条和第一份文档里的
"前端校验不算校验"是一个道理。

### 4.5 扇出控制：把 O(N²) 压到 O(N·k)

这是 SFU 性能的核心，按优先级：

1. **可见性订阅（最有效）**：客户端只订阅**当前屏幕上看得到的 tile**（9 宫格就订 9 路 + 固定的 1 路主讲）。
   滑动/翻页时动态 `subscribe`/`unsubscribe`。→ 把 N² 直接砍成 N×9。
2. **Simulcast 三层**（q/h/f）：发布端同时推 3 档（如 180p/360p/720p），
   SFU 按接收者的 tile 尺寸和可用带宽**选择性转发其中一层**。
   9 宫格里的小 tile 只发 180p，主讲大屏才发 720p。→ 出口带宽再降 3~5 倍。
3. **last-N**：只转发最近 N 个活跃说话人的视频（N=4~9），其余人显示头像占位。
4. **切层要用 PLI 请求关键帧**：切层时接收端会花屏，必须立刻向发布端请求关键帧（`producer.requestKeyFrame()`），
   否则用户会看到几百毫秒的雪花。**这个细节能证明你真的调过 SFU，而不只是看过架构图。**
5. **时间层（temporal layer）**：弱网接收者先丢时间层（降帧率）而不是降分辨率，观感更好。

### 4.6 客户端渲染：几十个 `<video>` 会把浏览器搞崩

这是多人场景最容易被忽略、但一定会撞上的问题：

- 每个 `<video>` + 解码器都占内存/GPU，20 个以上就明显掉帧，50 个直接崩。
- 做法：**虚拟化 tile**——只创建约 12 个 `<video>` 元素循环复用（类似列表回收），
  按布局位置绑定不同的 stream；不可见的 tile 立刻 `unsubscribe` 并 `srcObject = null`。
- 布局模式：宫格 / 主讲+缩略条 / 侧边栏；切布局时重建订阅集合。
- 移动端限制最大分辨率与解码数，`RTCRtpReceiver` 用 `playoutDelayHint` 平衡延迟与流畅。

### 4.7 安全模型变了：SFU 不是端到端加密（修正我之前的说法）

⚠️ **这里要修正我之前对你说过的话。**

一对一 P2P 时，媒体是 DTLS-SRTP **端到端**加密，信令服务器看不到内容——所以我说"信令无鉴权不等于通话不安全"。
**但引入 SFU 后不成立了**：

```
P2P:   浏览器A ←── 端到端加密 ──→ 浏览器B          服务器什么都看不到
SFU:   浏览器A ←─SRTP─→ SFU ←─SRTP─→ 浏览器B       SFU 能解密所有音视频
```

补救手段：

- **SFrame / Insertable Streams（E2EE）**：客户端之间额外做一层帧级加密，SFU 只转发密文，
  连 layer 切换都只能靠 RTP 头里的非加密字段——这是 Google Meet / LiveKit E2EE 的做法。
- 或者接受"SFU 是可信的"，用严格的访问控制 + 全链路 TLS + 不落盘来降低风险。

**面试里主动指出这一点，比等着被问要好得多**，因为它证明你知道自己的架构把信任边界挪到了哪里。

### 4.8 与现有领域模型的衔接（`CONTEXT.md` 可以直接复用）

| `CONTEXT.md` 里的概念 | 单机一对一实现 | 多人 SFU 实现 |
|---|---|---|
| 未开启设备 | 无 track | 无 producer |
| 已关闭设备（设备仍占用） | `track.enabled = false` | **`producer.pause()`**（客户端仍持有设备，服务端停转发） |
| 开启设备 | track enabled | producer active |
| 挂断 | **结束通话 + 离开房间**（房间持久存在） | 建议改为：`bye` 只结束本端媒体，`leave_room` 才离开房间——否则一人挂断会打断整场 |
| 房间存在性 | PostgreSQL（`rooms` 表），由 auth 服务校验并签发 `roomToken` | 同样适用：多人房间更需要在库里持久化容量/权限 |
| 响应方让步（perfect negotiation） | 对端浏览器 | 与 SFU 协商时同样适用（多数实现是客户端 offer / SFU answer，订阅变化时 SFU 侧可发起 offer，具体看所选 SFU 文档） |
| 对方已关闭摄像头 | `video_mute` 消息 | `peer_track{state:"paused"}`，按 peerId 维护一张表 |

**注意 `track.enabled=false` 在这里是个陷阱**：它只是持续发送黑帧（甚至更糟——编码器把黑帧压得很小但仍占包量），
**带宽并不会真省下来**。多人场景必须用 producer 级 pause。这也解释了为什么单人版的"关闭摄像头"
在人数上去之后必须重新实现。

## 5. 容量模型：这次是 CPU 和带宽**双约束**

```
单路转发 720p 的经验值（必须自己实测，这里给量级）：
  出口带宽 ≈ 1.5 ~ 2.5 Mbps
  包速率   ≈ 500 ~ 1000 pps
  CPU      ≈ 单核的 2% ~ 5%（纯转发、不解码）

单节点 16 vCPU + 1 Gbps：
  带宽上限 ≈ 1000 Mbps / 2 Mbps        ≈ 500 路
  CPU 上限  ≈ 16 / 0.03                ≈ 530 路
  → 两者相当，都落在 500 路附近
```

**结论（要背下来）：SFU 是少见的"CPU 和带宽同时逼近上限"的场景，所以扩容必须同时看两个指标。**

一个 100 人房间的出口预算（按 §4.5 优化后，假设 9 路视频 / 其余音频）：

```
9 路视频 × 平均 0.8 Mbps（小 tile 走 180p）+ 100 路音频 × 0.05 Mbps
≈ 7.2 + 5 = 12.2 Mbps / 房间
→ 1 Gbps 出口约可承载 80 个这样的 100 人房间
```

对比不优化的最坏情况（人人开 720p 互相订阅）：单房间就是 14.8 Gbps，**一个房间都开不起来**。
这个对比就是 §4.5 全部优化的价值所在。

### 房间规模分级（面试时按这个表回答"能支持多少人"）

| 场景 | 人数 | 拓扑与手段 | 服务器成本 |
|---|---|---|---|
| 小组会议 | 2~9 | SFU 全量转发 + simulcast | 极低 |
| 中会 | 10~50 | 可见性订阅 + last-N(9) + 大流降分辨率 | 低 |
| 大会 | 50~500 | 角色化（少数人推流）+ 默认不订视频 + 音频优先 | 中 |
| 直播 | 1k~100k | **WebRTC 只做低延迟层，大规模走 CDN**（见 §6） | 取决于 CDN |

## 6. 直播场景：WebRTC 不该一个人扛完

如果"类似直播"意味着**几万人观看**，用 WebRTC SFU 给每个人转发是**错的**——
它是为低延迟交互设计的，成本随观众数线性上涨（1 万观众 × 2 Mbps = 20 Gbps）。

正确的分层：

```
主播 ──WebRTC/RTMP──▶ SFU ──┬── WebRTC 直连（<1s 延迟）→ 前 N 个观众（连麦/互动位）
                            └── RTMP/HLS/LL-HLS ──▶ CDN ──▶ 海量观众（3~10s 延迟）
```

| 层 | 观众数 | 延迟 | 适用 |
|---|---|---|---|
| WebRTC(SFU) | 数十~数百 | < 1 s | 需要连麦、送礼实时反馈的核心观众 |
| LL-HLS / WebRTC-to-CDN | 数千~数万 | 2~5 s | 普通观众 |
| HLS / FLV | 无上限 | 5~30 s | 大规模 |

**"何时用 WebRTC、何时用 CDN"是直播架构最核心的取舍**，能讲清楚这个分层的候选人不会多。

## 7. 高可用：故障域比一对一大了

| 故障 | 影响面 | 恢复手段 | 目标 RTO |
|---|---|---|---|
| 单个客户端断网 | 1 人 | 客户端重连 + 重新 publish/subscribe（已有指数退避） | < 5 s |
| **信令节点挂** | 只影响它上面的连接 | 换节点重连（房间状态在 Redis），见第一份文档 | < 5 s |
| **SFU 节点挂** | **它承载的所有房间全灭** | 调度器把房间重新分配到新 SFU，客户端重新 publish；花名册从 Redis 恢复 | < 10 s（要实测） |
| Redis 挂 | 调度与花名册不可用 | 主从 + Sentinel；降级为"拒绝新房间、保住现有房间"（**已有房间不依赖 Redis 也能继续** <- 这点设计时要保证） | 取决于切换 |
| 出口带宽打满 | 全节点通话质量下降 | 水位线 + 准入控制（`no_capacity`），优先保护已在线房间 | 立即 |

**必须做的故障演练**（第一份文档里的第 3、4 张表，在这里扩展）：

1. `kill -9` 一个 SFU → 记录受影响房间数、重分配耗时、重新出画面耗时（p50/p99）、成功率。
2. 滚动重启 SFU 节点 → 通话中断率。
3. 把一个 SFU 的出口带宽打满 → 观察调度器是否正确停止分配新房间、已在线房间是否被保护。
4. Redis 主从切换 → 新房间能否加入、已有房间是否受影响。

**爆炸半径要写进文档**："单 SFU 故障影响 ≤ 该节点承载的房间数，占全局 < X%，恢复时间 p99 = Y s"。

## 8. 路线图

| 阶段 | 内容 | 工作量 | 产出 |
|---|---|---|---|
| **P0 协议与 UI 多人化** | 花名册、`peer_*` 事件、宫格 UI、虚拟化 tile、可见性订阅；**媒体先用 Mesh，硬限 4 人** | 1~2 周 | 多人界面与信令状态机能跑通，作为过渡（**明确写"Mesh 上限 4 人，仅过渡"**） |
| **P1 接入 SFU** | 集成 mediasoup worker 池、`roomToken`、单 SFU 节点、会议模式 ≤20 人、simulcast、producer pause | 2~4 周 | 单节点 SFU 可用的多人通话 |
| **P2 调度与多节点** ⭐ | 房间→SFU 调度器、负载上报、水位线准入、Redis 化房间分配、多 SFU + 故障重分配 | 2~3 周 | **"高并发高可用"的核心产出**：N 节点集群 + 故障演练数字 |
| **P3 直播分层** | 角色/发布权限、默认不订视频、RTMP/HLS 推到 CDN、LL-HLS 播放 | 2~3 周 | 支持大规模观看的直播模式 |
| **P4 可选** | SFrame E2EE、跨区级联 SFU、录制 | 数周 | 加分项 |

**顺序建议：P0 → P1 → P2 一定要做完**，因为 P2 才是"分布式后端"的证明。
P3 可以只做设计、把关键结论写进文档（"我用 WebRTC 做低延迟层 + CDN 做大规模层"）。

### 部署要点（会重演你在 coturn 上踩过的坑）

- mediasoup 每个 worker 需要一段 **RTC 端口范围**（UDP+TCP），必须像 coturn 那样在**云安全组**放行。
- **`announcedAddress` / `listenInfos` 必须填公网 IP**——这正是你 `deploy_turn.sh` 里
  `relay-ip` 那个坑的同一个成因（EIP 经 NAT 映射，本机网卡上没有公网 IP）。
- worker 数 = CPU 核数；房间粘在 worker 上（`Router` 不跨 worker）。
- 一台机器上多 worker 时，端口段要错开，避免冲突。

## 9. 面试怎么讲 & 简历 bullet

### 这套东西让你能接住的问题

| 问题 | 回答要点 |
|---|---|
| 为什么不用 Mesh？ | 上行 = (N-1)×bitrate，N=6 就要 7.5 Mbps，家宽/手机扛不住；房间总流量 O(N²)。 |
| SFU 和 MCU 的区别？ | SFU 纯转发不解码，CPU 低、保留每人独立布局；MCU 混流，CPU 高但出口 O(N)，适合导播/录制。 |
| 扇出怎么控制？ | 可见性订阅 → simulcast 选层 → last-N → 切层发 PLI。给出优化前后的出口带宽对比数字。 |
| 房间怎么调度到机器上？ | 加权最小负载 + spread 策略 + 70% 水位线准入；讲清楚 packing vs spread 的爆炸半径取舍。 |
| SFU 节点挂了怎么办？ | 爆炸半径 = 该节点房间数；重新分配 + 客户端重 publish；给出实测 RTO。为什么不选 1+1 热备（成本）。 |
| 你还是端到端加密吗？ | **不是**。SFU 终结 DTLS/SRTP，能解密媒体；要 E2EE 得上 SFrame/Insertable Streams。 |
| 一万人观看怎么设计？ | WebRTC 只做 <1s 的低延迟层给互动位，海量观众走 LL-HLS/CDN；不要用 SFU 硬扛。 |
| 关闭摄像头省带宽吗？ | `track.enabled=false` 只发黑帧，**不省**；必须 `producer.pause()` 让 SFU 停转发。 |

## 10. 不要做的事

| 不要做 | 原因 |
|---|---|
| 自己从零写 SFU | 数月工作量，且要处理 NACK/RTX/PLI/TWCC/simulcast/拥塞控制，性价比极低 |
| 全房间 Mesh 然后宣称支持 20 人 | 一压就崩，且面试官会当场算上行带宽 |
| 用 `track.enabled=false` 当"关摄像头省带宽" | 黑帧照样占带宽，多人场景必须服务端 pause |
| 用 WebRTC SFU 硬扛上万观众 | 成本 O(N)，正确做法是分层 + CDN |
| 把 Router 跨节点共享 / 让媒体跨节点流动 | 媒体跨节点转发成本极高，房间必须粘在一个 SFU |
| 为了"高并发"提前上 K8s/Service Mesh | 3~5 个节点用 systemd + 脚本足够，讲不出解决的具体问题反而扣分 |

## 11. 和一对一版本的关系（要不要保留？）

**建议同时保留两条路径**，这是设计上的加分项：

- 房间人数 ≤ 2 且 P2P 可达 → 走你现有的 P2P 直连方案（**零服务器媒体成本，延迟最低**）。
- 人数 > 2 或 P2P 不可达 → 分配 SFU。

这就是真实的 WebRTC 产品（如 Meet、Zoom）都在做的**自适应拓扑**。面试时能说
"我按人数和网络条件在 P2P 与 SFU 之间自适应切换，2 人通话完全不消耗服务器媒体资源"，
比"我做了个 SFU"更能体现你会算成本。

实现上：`CONTEXT.md` 的"响应方让步"领域模型、客户端已有的 perfect negotiation 与 ICE restart 逻辑
**在两个拓扑下都能复用**，主要工作量在信令协议扩展（§4.3）与客户端渲染（§4.6）。
