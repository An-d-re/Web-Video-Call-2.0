## 一、一页纸摘要

**是什么**：一个自建的实时音视频通话平台。浏览器之间直接传输加密的音频视频，自研信令服务负责把两端"牵上线"；
P2P 打不通时由自建 TURN 服务器中继。支持一对一到多人、从会议到直播的多种形态。

**为什么做**：现有开源方案（Jitsi、LiveKit）把信令与调度全部内置，用起来学不到东西；
从零实现信令、ICE 协商、房间状态机、故障恢复与集群调度，才能真正掌握实时通信的完整链路。

**当前状态**：v1.0 已在阿里云上跑通公网一对一通话（HTTPS + WSS + TURN 全链路自建），
包含 perfect negotiation、ICE 自动恢复、断线重连、半开连接回收等完整可靠性机制。

**下一阶段目标**：把一对一扩展为"多人自由开关视频"的房间，并让系统具备**可测量**的
高并发（多节点集群）与高可用（节点故障秒级恢复）能力。

**关键判断（本方案的地基）**：

> **信令层天生不是瓶颈，媒体层才是。**
> 一对一 → 信令只是转发几 KB 的 SDP/ICE，而 TURN 中继每路通话持续占用双向约 3 Mbps。
> 多人 → 拓扑必须从"全互联"换成 SFU，瓶颈从带宽变成 **CPU 与带宽双约束**，
> 并第一次真正产生"把有状态的房间调度到某台机器上"这个分布式问题。

这个判断决定了整个技术路线：**先做单机健壮性与可观测 → 再做无状态化与集群调度 → 最后做媒体面扩展**。
跳过前两步直接上分布式中间件，是拿不到可讲清楚的成果的。

## 二、项目定位

### 2.1 解决的痛点

| 痛点 | 现状 | 本项目的做法 |
|---|---|---|
| 实时音视频门槛高 | 涉及 SDP 协商、ICE 穿透、NAT 类型、媒体加密等一整套协议 | 从零实现完整链路，每一层都能讲清楚 |
| 现成方案是黑盒 | 调 API 能跑，但不知道为什么 | 信令、房间状态机、TURN 部署、集群调度全部自建 |
| 弱网体验差 | 断线即中断、切网就卡死 | ICE 自动重启、信令断线重连、半开连接回收、节点故障重分配 |
| 多人成本失控 | 全互联拓扑上行带宽随人数平方增长 | SFU 转发 + 可见性订阅 + Simulcast 选层，把出口压回线性 |

### 2.2 目标场景

| 场景 | 人数 | 形态 | 版本 |
|---|---|---|---|
| 一对一视频通话 | 2 | P2P 直连，零服务器媒体成本 | **v1.0 已实现** |
| 小组会议 | 3~9 | SFU 转发，人人可开视频 | v2.0 |
| 中型会议 | 10~50 | SFU + 可见性订阅 + last-N 控制扇出 | v2.0 |
| 大会 / 公开课 | 50~500 | 角色化，少数人推流，观众默认只订音频 | v2.5 |
| 直播 + 连麦 | 1k+ | WebRTC 做低延迟层，海量观众走 CDN | v3.0 |

### 2.3 核心价值主张

1. **全链路自建**：从 WebSocket 握手、SDP 协商、ICE 穿透到 TURN/SFU 集群，没有黑盒。
2. **成本可控**：2 人通话不消耗服务器媒体资源（P2P）；多人场景通过扇出控制把出口带宽压到最低。
3. **可测量**：所有性能与可用性指标都有压测与故障演练数据支撑，不是架构图上的承诺。

## 三、系统架构

### 3.1 当前架构（v1.0）

```
   ┌───────────┐                                        ┌───────────┐
   │ 浏览器 A  │                                        │ 浏览器 B  │
   └─────┬─────┘                                        └─────┬─────┘
         │  HTTPS(页面) / WSS(信令)                            │
         └───────────────────┬────────────────────────────────┘
                             │
                  ┌──────────▼───────────┐
                  │  nginx  (443, TLS)   │  · 静态托管 static/index.html
                  │                      │  · /ws → 127.0.0.1:8888 反代
                  └──────────┬───────────┘
                             │ WebSocket
                  ┌──────────▼─────────────────────┐
                  │  signaling  server.cpp         │
                  │  C++17 / muduo  · 端口 8888     │
                  │  ────────────────────────────  │
                  │  · 房间表（内存，最多 2 人）    │
                  │  · 信令转发（SDP / ICE / 状态）  │
                  │  · 心跳存活 + 半开连接回收       │
                  │  · ICE 配置下发（读 turn_config）│
                  └────────────────────────────────┘
                             │
              ┌──────────────┴───────────────┐
              │                              │
   ┌──────────▼─────────┐         ┌──────────▼─────────┐
   │ 媒体：P2P 直连      │  打不通  │ coturn (3478 +      │
   │ DTLS-SRTP 端到端加密│ ──────▶ │ 49152-65535/udp)    │
   └────────────────────┘         └────────────────────┘
```

**特点**：信令是单进程、内存态、无持久化；媒体尽量不经过服务器。

### 3.2 目标架构（v2.5：多人 + 集群）

```
   ┌──────────────────── 客户端 ─────────────────────┐
   │  ①信令 WSS → signaling 集群（无状态）             │
   │  ②媒体 UDP/TCP → 被调度到的 SFU 节点             │
   └──────┬──────────────────────────────┬───────────┘
          │                              │
   ┌──────▼───────────┐                  │
   │ signaling-1..N   │  无状态：         │
   │  · 鉴权 / 签发token                 │
   │  · 房间→SFU 调度 │                  │
   │  · 花名册/在线态  │                  │
   └───┬──────────┬───┘                  │
       │          │                      │
  ┌────▼────┐ ┌───▼────────────┐         │
  │ Redis   │ │ SFU 调度器      │         │
  │ room→sfu│ │ 加权最小负载     │         │
  │presence │ │ +spread+水位线  │         │
  └─────────┘ └───┬────────────┘         │
                  │ 心跳 + 负载上报        │
   ┌──────────────▼──────────────────────▼────────┐
   │  SFU 集群（有状态 · CPU 密集 · 房间粘性）      │
   │  mediasoup worker 池：Router→Transport→       │
   │  Producer/Consumer，纯 RTP 转发不解码          │
   └───────────────────┬───────────────────────────┘
                       │
              TURN（仅 UDP 被封的客户端）
```

**三条主线**：

1. **信令面无状态化**：它不再"拥有"房间，只做鉴权、调度决策、花名册查询 → 可任意增减节点。
2. **媒体面有状态**：一个房间的媒体转发必须固定在同一个 SFU 进程（媒体跨节点搬运成本极高）→
   产生"房间 → SFU"的调度问题。
3. **两个平面独立扩容**：信令按连接数扩，SFU 按 CPU + 出口带宽扩。

### 3.3 关键流程（v1.0 已实现）

```
A                            signaling                        B
│  join_room{roomId}            │                             │
├──────────────────────────────▶│                             │
│◀───────── joined{roomId,peers}│                             │
│                               │◀──── join_room{roomId} ─────┤
│                               ├──── joined ────────────────▶│
│◀──── start_call{initiator:1,  │                             │
│        iceServers[]} ─────────┼──── start_call{initiator:0, │
│                               │       iceServers[]} ───────▶│
│                               │                             │
│──── offer ───────────────────▶├──── offer ─────────────────▶│
│◀─── answer ───────────────────┤◀─── answer ─────────────────│
│──── ice ⇄ ────────────────────┤──── ice ⇄ ──────────────────│
│                               │                             │
│◀══════════ 媒体：P2P 直连 或 TURN 中继（不经过信令） ═══════▶│
│                               │                             │
│──── bye ─────────────────────▶├──── bye ───────────────────▶│
│◀─── bye_ack ──────────────────│                             │
│  （挂断 = 结束通话 + 离开房间；房间本身持久保留，可再次进入）  │
```

## 四、功能清单

图例：✅ 已实现　🔨 规划中　💡 可选加分项

### 4.1 房间与信令（✅）

| 编号 | 功能 | 状态 | 说明 |
|---|---|---|---|
| A1 | 创建房间 | ✅ | 填标题 + 可选密码；**房间号由服务端生成**（32 字符表，排除易混字符），撞号自动重试 |
| A2 | 加入房间 | ✅ | 从列表点击或输入房间号；加密房间需输密码（4~8 位），错 5 次锁 60 秒 |
| A3 | 入房确认（joined ack） | ✅ | 客户端收到 ack 才认为进房成功，避免"界面已进房、服务端没进" |
| A4 | 重复入房幂等 | ✅ | 同一连接重复 join 同一房间不产生重复成员，且 `joined.inCall` 如实告知"通话进行中" |
| A5 | 挂断并离开房间 | ✅ | `bye` = 结束通话 + 离开房间；房间持久保留，可从"我的房间"再次进入 |
| A6 | 一连接一房间 | ✅ | 换房时自动从旧房间摘除并通知旧对端 |
| A7 | 信令转发 | ✅ | offer / answer / ice 原样转发，服务端不解析媒体内容 |
| A8 | 心跳与半开连接回收 | ✅ | 30s ping，连续两次无 pong 判定失联并回收（≤60s） |
| A9 | **房间持久化** | ✅ | 房间标题/密码/创建者/加入记录存 PostgreSQL；重启不丢 |
| A10 | **房间列表** | ✅ | 侧栏两个 Tab：活跃房间（实时在线人数）、我的房间（加入记录） |
| A11 | **进房凭证** | ✅ | auth 校验密码后签发 2 分钟有效的 `roomToken`，信令服务只验签取 roomId |
| A12 | **解散房间** | ✅ | 仅创建者可解散；「我的房间」里自己的房间带 `×`，二次确认后删除；解散后房间号与加入记录一并消失，房内其他人 4 秒内收到"已被创建者解散"并被退出 |

## 五、技术栈

### 5.1 现状（v1.0）

| 层次 | 技术 | 用途 | 为什么选它 | 替代方案 |
|---|---|---|---|---|
| **前端** | 原生 HTML/CSS/JS（单文件） | 界面与信令客户端 | 零构建、零依赖，便于部署与调试 | Vue/React + Vite（规模上来后再拆） |
| | WebRTC API | `RTCPeerConnection`、`getUserMedia` | 浏览器原生，无需插件 | — |
| | WebSocket API | 信令通道 | 全双工、低延迟 | SSE（不支持双向） |
| **后端** | C++17 | 信令服务实现语言 | 高性能、可控内存、贴近底层协议 | Go（生态好但媒体库偏新） |
| | **muduo** | 网络库（Reactor + 多线程） | 国内 C++ 面试认可度高，源码可读，线程模型清晰 | libevent / Boost.Asio |
| | **jsoncpp** | 信令消息序列化 | 轻量、API 简单 | nlohmann/json（header-only，但编译慢） |
| | **OpenSSL** | SHA1（WS 握手校验）、Base64 | 系统自带、稳定 | 自研（不必要） |
| | 自研 WebSocket 帧处理 | 握手、掩码解码、分片重组、控制帧 | 不引入额外依赖，完全掌控协议细节 | libwebsockets / uWebSockets |
| | AsyncLogging | 异步滚动日志 | muduo 自带，不阻塞 IO 线程 | spdlog |
| **协议** | WebSocket（RFC 6455） | 信令传输 | 浏览器原生支持 | Socket.IO（更重） |
| | 自定义 JSON 信令（11 种消息） | 业务控制 | 简单直观、易调试 | Protobuf（更省带宽但可读性差） |
| | SDP / ICE / STUN / TURN | 媒体协商与穿透 | WebRTC 标准 | — |
| | DTLS-SRTP | 媒体加密 | WebRTC 强制，端到端（v1.0 P2P 形态） | — |
| **媒体** | P2P 直连 | 2 人通话媒体传输 | 零服务器带宽成本、延迟最低 | 全部走 TURN（成本高） |
| | **coturn** | NAT 穿透失败时的中继 | 事实标准、成熟稳定 | 自研 TURN（无意义） |
| **部署** | 阿里云 ECS | 服务器 | 国内网络可达 | — |
| | **nginx** | TLS 终止、WSS 反代、静态托管 | 运维标配 | Caddy（自动证书，但可控性弱） |
| | 自签证书（含 IP SAN） | 满足安全上下文要求 | 无域名也能启用 HTTPS | 正式域名 + Let's Encrypt（长期方案） |
| | systemd | 服务守护与自启 | 系统标准 | supervisor |
| | 云安全组 | 端口放行 | 云平台强制 | — |

### 5.2 规划新增（v2.x / v3.0）

| 层次 | 技术 | 用途 | 为什么选它 |
|---|---|---|---|
| **媒体** | **mediasoup**（C++ SFU） | 多人媒体转发 | 与现有 C++ 技术栈衔接自然；只做 SFU，调度与信令自研 |

| | Redis Sentinel | Redis 高可用 | 主从自动切换 |
| **消息总线** | Redis Pub/Sub（分片） | 信令跨节点路由 | 信令量级小，广播模型足够；无需引入 MQ |
| | NATS（可选） | 主题精准路由 | 节点数 >20 时替换 Pub/Sub，避免广播放大 |
| **鉴权** | HMAC-SHA256 / JWT | `roomToken` / `reconnectToken` | 无状态、可过期、SFU 可独立验签 |
| **可观测** | **Prometheus + Grafana** | 指标采集与看板 | 业界标配，能直接出压测图表 |
| | 自研 `/healthz` `/readyz` `/metrics` | 探针与指标暴露 | 复用现有 HTTP 处理分支，改动小 |
| **压测** | **k6**（`k6/ws`） | 信令连接数与延迟压测 | 脚本化、输出 p95/p99 |
| | Puppeteer（假摄像头） | 真实端到端媒体验证 | 无需硬件，可批量 |
| | `turnutils_uclient` | TURN 中继压力测试 | coturn 自带 |
| **直播** | LL-HLS / RTMP + CDN | 海量观众分发 | WebRTC 不适合万人扇出 |
| **加密（可选）** | SFrame / Insertable Streams | SFU 场景恢复端到端加密 | Meet / LiveKit E2EE 的做法 |
| **本地演练** | Docker Compose | 本机起 3 节点 + Redis 做故障演练 | 不必买多台云主机 |

## 六、关键技术方案（摘要）

详细论证见附录两份文档，这里只列结论。

| # | 决策 | 结论 | 核心理由 |
|---|---|---|---|
| 1 | 信令是否需要鉴权才能通话？ | **不需要** | WebRTC 媒体是 DTLS-SRTP 加密的，信令服务器只是转发器。鉴权解决"谁有资格用资源"，不是"通话能否建立" |
| 2 | 分布式路由用什么？ | **无状态节点 + Redis presence + Pub/Sub 分片** | 一致性哈希粘性路由**恰好在扩容时坏掉**（新连接落到新节点、老对端还在老节点） |
| 3 | 房间状态要不要强一致持久化？ | **不要** | 通话是分钟级易失会话，丢了让客户端重连重建；强一致收益 < 成本 |
| 4 | 故障恢复靠服务端复制还是客户端重建？ | **客户端重建 + 座位接管 token** | 成本低一个数量级，且 RTO 可测量、可写进指标 |
| 5 | 多人用什么拓扑？ | **SFU**（Mesh 上行 O(N) 会死，MCU 的 CPU 太贵） | 每人 1 路上行，客户端复杂度也大幅下降 |
| 6 | 扇出怎么控制？ | 可见性订阅 → Simulcast 选层 → last-N → 切层发 PLI | 把 100 人房间出口从最坏 14.8 Gbps 压到约 12 Mbps |
| 7 | 关闭摄像头能省带宽吗？ | **`track.enabled=false` 不能**，必须 `producer.pause()` | 前者只发黑帧照样占带宽，多人场景会累积成灾难 |
| 8 | 房间怎么调度到机器？ | 加权最小负载 + **spread** + 70% 水位线准入 | spread 缩小爆炸半径；宁可拒绝新房间也不让在线房间集体劣化 |
| 9 | 直播怎么做？ | WebRTC 只做 <1s 低延迟层，海量观众走 CDN/HLS | 给 1 万观众做 SFU 扇出 = 20 Gbps，成本不可接受 |
| 10 | 引入 SFU 后还是端到端加密吗？ | **不是**。SFU 终结 DTLS/SRTP，能解密媒体 | 需要 SFrame/E2EE 才能恢复；信任边界挪到了 SFU 节点 |

## 七、容量与性能指标

### 7.1 目标 SLO

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 通话建立成功率 | ≥ 98% | 端到端自动化（Puppeteer）批量建通话 |
| 首帧时间（TTFF） | p95 < 2 s | 从 `start_call` 到远端画面出现 |
| 信令入房延迟 | p99 < 50 ms | 从 `join_room` 到 `joined` |
| 信令转发延迟 | p99 < 20 ms（同机房） | offer/answer/ice 往返 |
| 单节点空闲连接 | ≥ 50,000 | k6 压测，观察 RSS 与 fd |
| **信令节点故障 RTO** | **< 5 s** | `kill -9` 后重新出现画面 |
| **SFU 节点故障 RTO** | < 10 s | 同上，含重新发布 |
| 滚动发布可用性 | 通话中断率 < 1% | 压测流量下滚动重启 |
| 单 SFU 中继/转发容量 | 需实测，目标 ≥ 300 路 720p | 压测 + 出口带宽监控 |

### 7.2 容量模型（面试可直接讲）

**信令层（不是瓶颈）**

```
单次通话信令总量 ≈ 10 ~ 20 KB（SDP 数 KB + ICE 候选数十条）
空闲连接内存     ≈ 2 ~ 5 KB / 连接
→ 1 万通电话/分钟 ≈ 20 Mbps 突发；单节点 10 万空闲连接 ≈ 数百 MB
```

**媒体层（真正的墙）**

```
TURN 中继单路成本  = 上行 + 下行 ≈ 1.5 + 1.5 = 3 Mbps
1 Gbps 网卡        ≈ 330 路（留 30% 余量 ≈ 230 路）

SFU 转发单路 720p  ≈ 1.5~2.5 Mbps、500~1000 pps、单核 2%~5%
16 vCPU + 1 Gbps   → 带宽上限 ≈ 500 路，CPU 上限 ≈ 530 路
→ SFU 是少见的"CPU 与带宽同时逼近上限"的场景，扩容要看双指标
```

**多人房间出口预算（优化后）**

```
100 人房间 = 9 路视频(平均 0.8 Mbps，小 tile 走 180p) + 100 路音频(0.05 Mbps)
           ≈ 7.2 + 5 = 12.2 Mbps / 房间
→ 1 Gbps 出口 ≈ 80 个这样的百人房间
不优化的最坏情况：单房间 14.8 Gbps（一间都开不起来）
```

### 7.3 成本模型（按带宽计费，需填入当地单价）

```
每月成本 ≈ 中继/转发出口流量(GB) × 单价 + 服务器台数 × 单价

关键杠杆：
  · P2P 直连成功率（国内经验：同城家宽 ~85%，4G ~60~70%）
    → 直连率每提高 10%，TURN 带宽成本直接下降对应比例
  · Simulcast 选层 + 可见性订阅（把 720p 需求降到 180p）
  · 拓扑自适应（2 人通话走 P2P，完全不产生媒体成本）
```

### 7.4 现状基线（v1.0，待补测）

| 项 | 现状 |
|---|---|
| 并发能力 | 单进程，无压测数据（**待补**） |
| 可观测性 | 只有日志文件 + 日志中的转发记录，无指标（**待补**） |
| 故障恢复 | 客户端重连 + 半开连接回收已实现；无节点级故障演练（**待补**） |
| 已知性能隐患 | 5 个全局 map + 5 把互斥锁；转发时线性扫描所有房间；`conn->send()` 无背压控制 |

## 八、里程碑与排期

| 阶段 | 内容 | 工作量 | 交付物（可写进简历/汇报） |
|---|---|---|---|
| **M0 收尾 v1.0** | 提交代码 + 打 tag；轮换已泄露的 TURN 口令；补 v1 的压测基线 | 1~2 天 | 可演示的公网一对一通话 + 基线数据 |
| **M1 单机健壮性** | `/healthz` `/readyz` `/metrics`；SIGTERM 优雅下线；背压水位线；限流；`conn→roomId` 索引；房间表 64 分片锁 | **2~4 天** | "接入 Prometheus 监控；全局锁改分片锁，1 万房间下转发 p99 从 __ ms 降至 __ ms" |
| **M2 多人通话** | 花名册 + 宫格 UI + 渲染虚拟化；接入 mediasoup；自由开关视频（producer pause）；可见性订阅 + Simulcast | 3~5 周 | "扩展为多人 SFU 架构，100 人房间出口带宽从最坏 __ Gbps 降至 __ Mbps" |
| **M3 规模化与高可用** ⭐ | 信令无状态化 + Redis；房间→SFU 调度器；水位线准入；token 鉴权；座位接管；SFU 故障重分配；故障演练 | 3~4 周 | **核心产出**："N 节点集群，kill -9 后 __ 个房间 __ 秒内恢复，成功率 __%" |
| **M4 直播分层** | 角色与发布权限；默认不订视频；RTMP/HLS → CDN；LL-HLS 播放 | 2~3 周 | "WebRTC 低延迟层 + CDN 大规模层，支持 __ 人观看" |
| **M5 可选** | SFrame E2EE；跨区级联 SFU；录制 | 数周 | 加分项 |

**排序理由**：

- **M1 必须在 M2/M3 之前**：没有指标与水位线控制，后面的分布式做没做对都不知道。
- **M3 是整个方案的重心**：后端岗位真正考察的是分布式与故障处理，M3 才产出这类证据。
- M4/M5 可以只做到设计层面，能讲清楚取舍即可。

## 九、风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| 范围过大 | 项目做不完，反而没有可讲成果 | 严格按 M1→M2→M3 推进；每阶段结束就固化数字、更新文档 |
| 无实测数据 | "高并发高可用"变成空话 | 每个里程碑必须交付一张压测/故障演练表 |
| 云上成本 | TURN/SFU 出口带宽按量计费 | 用 2~3 台按量实例做演练，用完释放；带宽核算脚本先算再做 |
| 自研 SFU 的诱惑 | 数月工作量，且打不过成熟方案 | **明确不自己写 SFU**，用 mediasoup，把精力放在调度层 |
| 过度设计 | 面试官一问细节就崩 | 文档里明确"非目标"与"刻意不做"，主动说明取舍 |
| 单机堆砌中间件 | 复杂度上升但讲不出解决什么问题 | 每个新增组件必须对应一个已量化的瓶颈 |
| Redis 成为单点 | 调度与花名册不可用 | 主从 + Sentinel；降级策略：拒绝新房间，保证**已有房间不依赖 Redis 也能继续** |
| 密钥/TURN 凭据泄露 | 被白用中继刷流量 | 凭据入环境变量、定期轮换；改用 REST 临时凭据 |

## 十、明确不做（非目标）

| 不做 | 原因 |
|---|---|
| 跨机房双活 | 分钟级会话，跨区同步的收益远小于成本 |
| 房间状态强一致持久化 | 易失状态 + 强一致是自找麻烦 |
| 自研 SFU / MCU | 数月工作量，且 RTP 重传、拥塞控制、Simulcast 等打不过成熟方案 |
| Kafka / RocketMQ 做信令总线 | 信令量级下 Redis Pub/Sub 足够，用 MQ 会被追问"为什么不用更轻的" |
| 提前上 K8s / Service Mesh | 3~5 个节点用 systemd + 脚本足够，讲不出解决的具体问题反而扣分 |
| 为"分布式"更换语言 | 语言不是难点，重踩网络库的坑是负收益 |
| 无实测的并发承诺 | 面试官一句"怎么压出来的"就结束了 |

### 11.2 术语表（详见 `CONTEXT.md`）

| 术语 | 含义 |
|---|---|
| 房间（Room） | 最多 2 人（v1.0）/ N 人（v2.0）的对等通话空间 |
| 发起方 / 响应方 | 重协商冲突时的 impolite / polite 角色 |
| SFU | Selective Forwarding Unit，只转发不混流的媒体服务器 |
| Mesh | 全互联拓扑，上行随人数线性增长，房间总流量 O(N²) |

| 设备三态 | 未开启（无 track）／已关闭（track.enabled=false，设备仍占用）／开启 |
| 半开连接 | TCP 未正常关闭、对端已失联的连接，靠心跳回收 |
| 爆炸半径 | 单个节点故障影响的房间/用户范围 |
| 水位线准入 | 节点负载超过阈值就拒绝新房间，保护在线房间 |
| 座位接管 | 客户端凭 token 在健康节点上抢回原房间座位 |

### 11.3 一句话总结

> 这个项目的价值不在于"用了一家大厂都在用的中间件"，
> 而在于**每一层都能说清楚为什么这么做、代价是什么、以及实测数据是多少**。
