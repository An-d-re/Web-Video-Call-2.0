# 演示脚本（v1.0）

> 目标：10 分钟内把「登录 → 建加密房间 → 通话 → 屏幕共享 → 质量面板/切设备/聊天/手机布局 → 异常恢复 → 挂断」走完，
> 每一步都能说出**它背后是哪段代码/哪个协议**，而不是只看到画面动。
>
> 演示环境：本机 VMware 里的 Ubuntu 24.04（`https://192.168.220.128`），
> 三个服务 `webrtc-auth`、`webrtc-signaling`、`coturn`，数据库 PostgreSQL。

---

## 〇、演示前 5 分钟：检查清单

在虚机里执行（或用 SSH）：

```bash
# 1) 三个服务都在跑
systemctl is-active webrtc-auth webrtc-signaling coturn
# 期望：active / active / active

# 2) 数据库连通（auth 服务的健康检查会真的 ping 一次 PG）
curl -sk https://127.0.0.1/api/health
# 期望：{"db":"ok","status":"ok","uptimeSeconds":...}

# 3) 证书没过期、SAN 里有演示用的 IP
sudo openssl x509 -in /etc/nginx/ssl/webrtc.crt -noout -dates -ext subjectAltName
# 期望：notAfter 在一年内；SAN 含 IP:192.168.220.128

# 4) 端口在听
ss -lntp | grep -E ':(80|443|8888|8080|3478)\b'
```

浏览器侧：

- 两台设备都打开 `https://192.168.220.128`，**看到证书警告要点「高级 → 继续前往」**（自签证书，正常现象）。
- 确认两台都有摄像头/麦克风权限；用耳机，避免回声。
- 提前注册好两个账号（注册有 5 次/分钟限流，现场连续注册两个号没问题，但别反复试错）。

房间数据清理（如果上次演示留了垃圾房间）：

```bash
sudo -u postgres psql -d webrtc -c "select id, title, owner_id from rooms order by created_at desc limit 10;"
# 需要删就 DELETE FROM rooms WHERE id='xxxx';（room_members 有级联删除）
```

## 一、主流程（10 分钟）

每一步都给了「操作 / 你该看到什么 / 一句话讲解」。

### 1. 登录与注册（40 秒）

- **操作**：A 机打开 `https://192.168.220.128` → 自动跳登录页 → 切「注册」→ 填用户名/昵称/密码 → 注册。
- **预期**：直接进主页，左上角显示「已登录：爱丽丝」。
- **讲解**：密码用 bcrypt（cost=12）存哈希，登录发两个令牌——访问令牌只放内存（XSS 拿不到持久凭证），刷新令牌走 `HttpOnly + SameSite=Strict` 的 Cookie，且每次刷新都轮换、旧的立刻作废。

### 2. 建一个加密房间（40 秒）

- **操作**：点侧边栏「+ 新建」→ 标题「答辩演示」→ 密码 `1234` → 创建。
- **预期**：自动进房，侧边栏出现这个房间（标题、创建者、🔒 标记、在线 1 人）。
- **讲解**：房间存在 PostgreSQL 里，不是内存里的临时对象，所以刷新页面、重启服务房间都还在。密码是 `sha256(salt + 口令)`，4~8 位，错 5 次锁 60 秒。

### 3. 第二台设备进房（40 秒）

- **操作**：B 机登录另一个账号 → 侧边栏点这个房间 → 弹密码框 → 输入 `1234`。
- **预期**：进房成功，双方状态栏变成「已加入房间，等待对方…」→「通话中」。
- **讲解**：进房不是直接把房间号发给信令服务，而是先向认证服务换一张**只对这一个房间有效、2 分钟过期**的 `roomToken`；信令服务只验签名，不连数据库。这样信令进程可以随便横向扩容。

### 4. 开摄像头和麦克风（40 秒）

- **操作**：两边各点「开启摄像头」「开启麦克风」。
- **预期**：本地预览出画面，远端也出画面；状态栏「通话中」。
- **讲解**：设备是**按需开启**的，进房不会偷偷抢摄像头。关闭摄像头用 `track.enabled=false`（对方看到「已关闭」），和「从未开启」是两个不同状态——这个区分在 `CONTEXT.md` 里有定义。

### 5. 屏幕共享（90 秒）★ 本轮新增

- **操作**：A 点「共享屏幕」→ 浏览器弹选择器 → 选「整个屏幕」或某个窗口 → 分享。
- **预期**：
  - A 的本地预览切成屏幕内容，左上角出现蓝色「正在共享屏幕」，摄像头按钮变灰。
  - B 的画面同步变成 A 的屏幕，右上角出现「对方正在共享屏幕」。
  - 过程中**画面不闪断**。
- **讲解**（这段是加分点）：共享不是新增一条视频轨，而是用 `RTCRtpSender.replaceTrack()` 把同一个 sender 上的源换掉。同 kind 替换不触发 `onnegotiationneeded`，**SDP 不重新协商、连接不断**，所以对方画面是平滑切过去的。如果用 `addTrack`，就要重协商一次，画面会短暂黑屏。
- **收尾**：再点一次「停止共享」，画面切回摄像头。

### 6. 通话质量面板 + 切换摄像头（60 秒）★ 本轮新增

- **操作**：A 指着远端画面右上角的小面板（码率/分辨率/往返/丢包/链路）→ 点标题折叠再展开 →
  点控制条上的「设备」→ 在弹出的窗口里换一个摄像头 → 再换一个麦克风。
- **预期**：
  - 面板每 2 秒刷新一次，链路显示「直连（P2P）」；码率随画面变化。
  - 折叠/展开有动画，不遮挡画面操作。
  - 换摄像头后**画面不黑、不中断**，B 那边一直有画面。
- **讲解**（加分点）：换设备走的是 `getUserMedia` 重新采集 + `RTCRtpSender.replaceTrack()`，
  和屏幕共享同一套思路——**不新增轨道，所以不重协商**。如果现场问"怎么证明"，可以直接说
  e2e 里断言了换轨后 `signalingState` 仍是 `stable`，并且旧轨 `readyState === 'ended'`。

### 7. 文字聊天（40 秒）★ 本轮新增

- **操作**：A 点控制条「聊天」→ 发一句「你好，能看到我的屏幕吗？」→ B 那边未读红点亮起 →
  B 点开抽屉看到消息。再让 A 发一条带尖括号的 `<img src=x onerror=alert(1)>`。
- **预期**：B 看到的是**这行字符本身**，不会弹窗、不会加载图片。
- **讲解**：聊天走同一条 WebSocket（`chat` 消息），服务端只做限长（500 字符，按字符截断不切坏汉字）
  和转发，**不落库**；前端只保留本次通话最近 100 条，用 `textContent` 渲染，所以对方塞 HTML 也没用。
  为什么不做持久化：这是通话的辅助通道，不是 IM，落库要连带做已读、离线、清理，收益不大。

### 8. 手机布局（30 秒）★ 本轮新增

- **操作**：开浏览器 DevTools → 切到手机模拟（390×844）→ 刷新页面重进房间。
- **预期**：远端画面铺满、本端变成右下角小窗、控制条贴底且按钮够大、页面没有横向滚动条。
- **讲解**：这套断点（≤750px）只用 CSS 重排，没有第二套页面；不过要如实说**只在模拟器里验过**，
  iOS 的自动播放与权限策略跟桌面不同，真机还要再调。

### 9. 模拟异常：对方关掉摄像头（30 秒）

- **操作**：B 点「关闭摄像头」。
- **预期**：A 的画面上盖「对方已关闭摄像头」遮罩，但**通话不断**，声音还在。
- **讲解**：这里刻意区分「关闭」和「未开启」。早期版本这两个状态混在一起，会出现「视频在播但 UI 说未开启」，是个真实修过的 bug。

### 10. 模拟异常：断网重连（60 秒）★ 最容易被问的点

- **操作**：把 B 机的网络断开 10 秒（关 Wi-Fi 或拔网线），再恢复。
- **预期**：A 侧短暂「连接中断」；B 恢复后自动重连 WebSocket、重新换 roomToken 入房，双方重新建立通话。
- **讲解**：前端退避重连有单飞保护（`connectPromise` + 单例 `reconnectTimer`），不会叠出多个 socket；后端对同一连接重复入房做了幂等，且一个连接只允许在一个房间，避免「幽灵成员」把房间占满。

### 11. 挂断（20 秒）

- **操作**：A 点「挂断」。
- **预期**：A 回到「未加入房间」；B 看到「对方已挂断，可以继续等待，或点『退出房间』离开」。
- **讲解**：挂断 = 结束通话 + 离开房间；`bye` 由服务端转发并释放座位。

## 二、兜底预案（现场出问题怎么办）

| 现象 | 原因 | 现场怎么救 |
|---|---|---|
| 页面打不开 / 提示不安全 | 自签证书 | 点「高级 → 继续前往」；**必须用 https**，`getUserMedia` 只在安全上下文可用 |
| 提示「摄像头被占用」 | 另一个程序（微信/腾讯会议）占着 | 关掉占用程序，重新点「开启摄像头」 |
| 远端画面全黑但有声音 | 浏览器拦了带声音的自动播放 | 页面会静音兜底并显示「🔇 点一下开启声音」，点一下即可 |
| 一直卡在「连接中」 | 同网段应能直连；跨网段没有中继 | 先在虚机跑 `bash /tmp/turn-check.sh` 确认 TURN 可用 |
| 「房间已满」 | 上次异常退出没释放座位 | 等约 1 分钟（心跳超时回收），或重启 `webrtc-signaling` |
| 注册提示「过于频繁」 | IP 限流 5 次/分钟 | 等 1 分钟，或直接用提前注册好的账号登录 |
| 「设备」弹窗里设备名是空的 | 还没授权过，浏览器不给 `deviceId`/`label` | 先点一次「开启摄像头」或「打开麦克风」授权，再点弹窗里的「刷新列表」 |
| 质量面板一直显示「-」 | 刚进通话、还没采到第二个样本 | 等 2~3 秒；码率是两次采样差分出来的 |
| 三个服务起不来 | 端口被占 / env 缺 JWT_SECRET | `journalctl -u webrtc-signaling -n 50`，看启动日志里的自检信息 |

## 三、加分材料（被追问时用）

**1. 证明 TURN 真的在转发媒体**

```bash
# 宿主机（仓库根目录）：强制所有 ICE 候选只走 relay，再看选中候选的类型
node tools/e2e/browser-e2e.js 192.168.220.128 --relay
```
输出里会有「A/B 的候选对本地是中继（媒体经 TURN 转发）」——同网段 P2P 本来就能通，**只有强制 relay 全绿才能证明 TURN 可用**。

**2. 三层测试的通过数**

| 层 | 命令 | 结果 |
|---|---|---|
| 协议层（直接说 WebSocket 协议） | `JWT_SECRET=<虚机密钥> node tools/e2e/ws-smoke.js 192.168.220.128 8888` | 36/36 |
| 全栈层（nginx + Go + PG + WSS） | `node tools/e2e/e2e-fullstack.js 192.168.220.128` | 34/34 |
| 浏览器层（真 Edge + 假摄像头，含屏幕共享/质量/聊天/手机布局） | `node tools/e2e/browser-e2e.js 192.168.220.128` | 57/57（强制中继 62/62） |

**3. 一句话架构**

> 信令用 C++/muduo 做长连接转发（只验 JWT 签名，不碰数据库），认证与房间元数据用 Go + PostgreSQL，
> nginx 统一入口（HTTPS + WSS 反代），媒体走 WebRTC P2P，跨网段时由 coturn 中继，
> 凭据是每次通话现签的临时用户名密码（coturn REST API），2 小时过期。

**4. 已知没有做的**（主动说，比被问出来好）

- 没做压测：并发上限目前只有设计文档里的容量模型，没有实测数字。
- 没做可观测性：没有 metrics/tracing，排障靠日志。
- 没做多人：只有一对一，多人 SFU 有设计文档、没有代码。
