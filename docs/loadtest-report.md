# 信令服务压测报告

> 被测对象：`server.cpp`（C++ / muduo 信令服务），部署在 4 核 4 GiB 的 Ubuntu 24.04 虚机上
> 压测工具：`tools/load/loadtest.js`（本仓库），从 Windows 宿主机跨机压测
> 数据来源：客户端自测往返 + 服务端 `/stats` 内部耗时，两边互相印证

**怎么读这份报告**：

- **没做过压测** → 按 1 → 2 → 3 → 11 的顺序读（11 是可以照着敲的手把手流程）
- **只想看结论** → 0 → 9（容量结论）
- **想看"怎么发现问题"** → 7（三个发现，比数字更值钱）
- **要复现或改工具** → 11 + `tools/load/README.md`

## 0. 一句话结论

**这台 4 核虚机跑到 2000 个 WebSocket 连接（1000 个满员房间）时，服务端内部转发 P95 只有 0.1 ms（优化前 0.5 ms），CPU 占用 7%（优化前 15%）。**

瓶颈不在信令服务器本身，而在三处：
1. **单进程 Node 压测客户端**（2000 连接时客户端自己就先崩了，P99 到 285 ms）；
2. **带宽**（媒体走 TURN，单路 3 Mbps，跟信令无关）；
3. **架构上限**（单进程 + 全局锁，能扛的量级是"单机几千连接"，不是"百万连接"——本来也没打算做到）。

如果明天要上线，按 **1000 连接起步、2000 连接封顶**做容量规划是安全的。

> 第 6.5 节是"阶段二改完再跑一遍"的前后对比：转发 P99 从 2.5 ms 降到 0.25 ms（−90%）。

## 1. 零基础：压测这件事的骨架

> 这一节写给"没手动做过压测"的人。有经验的话可以直接跳到第 4 节看结果。

### 1.1 压测到底在测什么

压测的本质是：**在不知道真实用户行为的前提下，用脚本模拟一群人同时使用系统，观察它在哪个环节先撑不住、撑不住时是什么表现。**

它回答三个不同层面的问题，很多人会把它们混成一个"性能如何"：

| 层面 | 问题 | 看什么数字 |
|---|---|---|
| 能力（Capacity） | 同时能服务多少人？拐点在哪？ | 连接数 / 房间数 vs 延迟、CPU |
| 延迟（Latency） | 每个人的等待时间是多少？最差的那批有多差？ | P50 / P95 / P99 |
| 稳定（Stability） | 跑久了会不会漏内存、漏 fd、延迟慢慢漂？ | RSS、fd 数、P95 随时间的变化 |

**为什么必须先有指标再压**：如果服务只告诉你"CPU 80%"，你无法区分是"锁竞争"还是"日志刷盘"还是"JSON 解析"。先把 `/stats` 这类内部计数做出来，压测才有解释力——这也是为什么本项目的顺序是"先做 `/stats`，再压"。

### 1.2 几种压测类型（名词别混）

| 类型 | 目的 | 加负载的方式 | 本项目做了吗 |
|---|---|---|---|
| **基准 Benchmark** | 固定参数反复跑，得到可对比的基线 | 参数不变，跑多遍 | ✅ S2（跑两遍验可重复性） |
| **容量 Capacity** | 从低到高逐档加，找出拐点 | 阶梯式爬坡 | ✅ S1（100/500/1000/2000） |
| **规模 Scale** | 某一维度单独放大，看谁先变慢 | 只改房间数 | ✅ S3（200→1000 房间） |
| **稳定性 Soak** | 长时间中等负载，抓泄漏 | 固定负载跑数小时 | ❌ S4 未跑（见第 10 节） |
| **尖峰 Spike** | 流量瞬间翻 10 倍，看会不会雪崩 | 瞬时打入 | ❌ 未做 |
| **压力 Stress** | 故意压到超过容量，看降级与恢复 | 超载 | ❌ 未做 |

**关键认知：先有基准，再谈优化。** 改代码前跑一遍、改完再跑同一套参数，才有资格说"优化了 30%"。没有基线的"优化"往往是自我感觉。

### 1.3 一次压测的完整流程（我们实际就是按这 7 步走的）

```
1. 把问题问清楚        "2000 连接会不会卡" 而不是 "测一下性能"
2. 先准备可观测性      服务端 /stats 就位，客户端能打点
3. 单连接验证脚本      1 房间 2 连接 + --trace，确认流程和断言都对
4. 小规模爬坡          10 → 100 → 500，每档确认错误率仍是 0
5. 定场景跑稳态        ramp-up 之后取稳态窗口（爬坡期数据要丢弃）
6. 跑两遍验证可重复    P50/P95/P99 两轮差异 < 10% 才算可信
7. 收尾 + 功能回归     重启服务清残留，跑 e2e 确认没把功能压坏
```

每一步"为什么"：

- **第 3 步最容易被跳过，也最容易出问题**。脚本有 bug 时，压测结果会告诉你"服务端很慢"，其实是脚本在等一个永远不会来的消息。先用 1 个房间跑通、看着 trace 逐条消息走完，后面才敢放大。
- **第 4 步是排除法**：如果 10 个连接就有错误，那是 bug 不是容量问题，别急着加量。
- **第 5 步的"稳态"**：ramp-up 阶段连接在陆续建立，延迟天然抖动，把这段算进去会污染结论。所以工具里 ramp-up 和 duration 是两个独立参数。
- **第 6 步是压测和"跑一次看看"的分界线**。只跑一次得到的数字，你不知道它是规律还是运气（我们在 5.2 就踩过这个坑：两轮数字一模一样，其实是因为统计没清零）。

### 1.4 术语速查

| 术语 | 含义 | 容易误解的地方 |
|---|---|---|
| 并发连接数 | 同时保持着的连接数 | 不等于"同时在线用户数"：一个人可能开多个标签页 |
| RTT | 一次往返的耗时（发出→收到回应） | 单程延迟通常取 RTT/2，但 TCP 握手是 1.5 个 RTT |
| P50 / P95 / P99 | 分位数：95% 的请求比它快 | 不是"平均"，也不能相加（两个 P95 不能平均成新 P95） |
| MAX | 单次最坏值 | 受单次抖动影响大，**不适合判断稳定性** |
| 吞吐 | 单位时间处理多少（条/秒、请求/秒） | 和延迟不是一回事：吞吐高但延迟可能也高（排队） |
| 错误率 | 失败请求占比 | 压测时先看它，非 0 就先停下查原因 |
| 饱和度 | 资源用掉多少（CPU、内存、fd、带宽） | 最危险的是"某个资源到 100% 但延迟还没涨"——拐点就在附近 |
| ramp-up（爬坡） | 用多长时间把负载加到目标值 | 太陡会测出"假瓶颈"（瞬间排队） |
| 稳态 | 负载加满后稳定运行的窗口 | 结论要从稳态窗口取，不要含爬坡 |
| think time | 模拟用户两次操作之间的停顿 | 不加 think time = 极限压测，不代表真实用户 |
| 拐点 / 膝盖（knee） | 负载继续加、延迟开始非线性上升的那个点 | 容量规划要定在拐点**之前**，留余量 |

## 2. 看哪些参数，为什么看它

### 2.1 三类指标，必须互相印证

| 类别 | 代表数字 | 回答什么 | 可信度 |
|---|---|---|---|
| **客户端侧** | 连接建立、auth、join、offer→answer、ICE 往返 | 用户实际等了多久 | 低——含压测机自身开销 |
| **服务端侧** | `/stats` 里的 `forward` / `join_room` 分位 | 服务端内部到底忙不忙 | 高——不含网络与客户端 |
| **系统侧** | CPU、RSS、fd、带宽 | 有没有资源见底 | 高——客观量 |

**只看一类必然出错**，第 7.3 节就是活例子：客户端 P99 285 ms、服务端 P95 0.5 ms，差 500 倍。

### 2.2 逐项说明：为什么看它、多少算正常

| 参数 | 是什么 | 为什么要看 | 我们实测 | 多少算正常 |
|---|---|---|---|---|
| **连接建立 P95** | TCP + WS 握手 + `auth` 完成的总时间 | 用户点"进入"到界面可用，最直观 | 5~25 ms | 内网 < 50 ms；公网 + 1 RTT |
| **auth RTT** | 发 `auth` 到收 `auth_ok`（含 JWT 验签） | 验签是纯 CPU 计算，能看出 CPU 是否吃紧 | 1~5 ms | < 10 ms |
| **join_room RTT** | 发 `join_room` 到收 `joined` | 包含占座 + 房间查找 + 配对派发，**最能暴露 O(n) 扫描** | 1~5 ms | < 20 ms |
| **offer→answer RTT** | 发起方发 offer 到收到 answer | 一次完整协商，等于"接通要等多久" | 2.5 ms（修 Nagle 前 50 ms） | < 100 ms（含浏览器侧处理） |
| **ICE 往返** | 稳态下一条小消息来回 | 纯转发路径的延迟，**最能反映服务端转发成本** | 2.5~10 ms | 内网 < 10 ms |
| **服务端 forward P95/P99** | 从收到消息到交给 socket 的内部耗时 | 排除了网络和客户端，**容量结论用它** | 0.25~0.5 ms | < 1 ms |
| **服务端 join P95** | 进房逻辑的内部耗时 | 房间数涨了它先涨 → 暴露锁与扫描 | 0.5~1 ms | < 2 ms |
| **错误数** | `error` 消息 + 超时 + 连接失败 | 非 0 就说明"还没到容量，已经出 bug" | 0 | 必须 0 |
| **CPU 占用** | 服务端进程用了多少核 | 饱和度的第一指标；也是"还能加多少"的依据 | 4.6%（400 连接）/ 15.3%（2000 连接，≈0.61 核） | < 70%，留 30% 余量 |
| **RSS 内存** | 常驻内存 | 泄漏检测：应随连接**线性**增长 | 4 KB/连接，2000 连接 32.6 MB | 线性增长 = 正常；指数增长 = 泄漏 |
| **fd 数量** | 打开的 file descriptor 数 | **最常见的泄漏点**：socket 不 close 就一直涨 | 连接数 + 22，严格线性 | 必须线性；涨到 `LimitNOFILE` 就再也接不了新连接 |
| **`LimitNOFILE`** | 进程 fd 上限 | 忘了它，1000 连接就 `EMFILE` | 65536（systemd 设的） | ≥ 期望连接数 × 1.5 |
| **带宽** | 出口/入口 Mbps | 媒体场景的真正瓶颈（信令只占几十 kbps） | 未压（TURN 单路约 3 Mbps） | 按"路数 × 单路码率"算 |

### 2.3 为什么看 P95/P99，不看平均值

平均值会被大量"很快"的请求掩盖。1000 个请求里 950 个 1 ms、50 个 500 ms，平均才 26 ms——看起来很美，但**每 20 个用户就有 1 个在等半秒**。

- **P50**：一半请求比它快，代表"常态"
- **P95**：95% 的请求比它快，代表"偶发卡顿"，一般拿它做 SLA
- **P99**：最差的那 1%，用户投诉基本来自这里
- **MAX**：极端值，看它是否离谱，**不用来判断稳定性**（一次 GC 就能改变它）

### 2.4 分桶会骗人：数字的精度是有限的

服务端延迟用固定分桶统计（微秒）：

```
100 / 250 / 500 / 1000 / 2500 / 5000 / 10000 / 25000 / 50000 / >50000
```

所以 `p50 = 100` 的意思是**"至少一半请求在 100 µs 以内"**，不是"就是 100 µs"。相邻两档差了 2.5 倍，所以你会看到报告里到处是 250、500、1000 这种数字——**那是桶边界，不是精确值**。

为什么用桶：分位数需要保存全部样本再排序，在每秒 1 万多条消息的热路径上做这件事不划算；固定桶只占几百字节，还天然支持"多轮/多进程合并"（把桶相加即可，不需要原始样本）。

代价：**精度只有 2.5 倍粒度**。对信令足够（谁在乎 80 µs 还是 120 µs），对"要做微秒级优化的场景"就不够了——那时候才需要 HDR Histogram 这类结构。

### 2.5 CPU 怎么算的（为什么不用 `top`）

读两次 `/proc/stat` 第一行（压测前后），取差值：总 tick 减去 idle，除以总 tick：

```bash
cat /proc/stat | head -1          # user nice system idle iowait ...
sleep 60
cat /proc/stat | head -1          # 再读一次，算差
```

- S2（400 连接）：**4.65%**
- S3（2000 连接、约 12 000 条消息/秒收发）：**15.3%** → 4 核算 **0.61 个核**

为什么不用 `top`：`top` 是采样+刷新，人工读数会有几秒误差，也没法算"这一段窗口内"的精确值；`/proc/stat` 是内核累计计数器，两次相减就是精确区间值，**可以直接写进脚本**。

> 注意 `/proc/stat` 是**整机**的，不是单进程的。这次虚机上只跑这一个吃 CPU 的服务，所以够用；多进程混跑时要读 `/proc/<pid>/stat`。

### 2.6 怎么读我们报告里的表（示范一次）

以 6.3 节的 S3 表为例，逐行读出结论：

| 你看到的 | 说明什么 |
|---|---|
| 入房 P50 250 → 250（不变） | **大多数请求没变慢**，说明没有全局性退化 |
| 入房 P95 500 → 1000（翻倍） | 变慢的是"偏慢的那 5%"，典型特征是**锁或扫描**：大部分时候很快，偶尔撞上遍历成本 |
| 转发 P95 也翻倍 | 转发也要找房间/找对端，同一个根因 |
| CPU 4.6% → 15.3% | 成本确实涨了 3 倍，但**绝对值还有 85% 余量** |
| 房间 ×5、延迟只 ×2 | 上升比线性慢 → 不是 O(n²) 卡死，是"有一定代价但可控" |

**这就是为什么必须同时看 P50 和 P95**：只看 P50 会得出"毫无影响"，只看 P95 会得出"性能腰斩"。真相是"中位数没动，长尾变长了"。

## 3. 用了什么工具，它们是什么

### 3.1 我们这次用的工具栈

| 工具 | 是什么 | 在压测里干什么 | 为什么用它 |
|---|---|---|---|
| **`tools/load/loadtest.js`** | 本项目自研的 Node 压测客户端（约 700 行） | 模拟几百上千个真实客户端，走完整业务流，记录每步耗时 | 见 3.2：现成工具测不了"有状态 + 自定义 JSON + JWT"的协议 |
| **`ws`** | Node 的 WebSocket 客户端库（npm） | 给脚本提供 WebSocket 连接 | 浏览器有原生 WS，Node 没有，这是最通用的实现 |
| **`/stats`** | 服务端内置的指标接口（本项目新增） | 提供连接数、房间数、消息/错误计数、内部耗时分位、RSS、fd | 没有内部数字，压测只能看 CPU，无法定位 |
| **`curl`** | 命令行 HTTP 客户端 | 手工验证 `/stats` 的鉴权（无 token 403、错 token 403、对 token 200）；也给 `/api/health` 探活 | 一行命令就能确认"是接口问题还是压测脚本问题" |
| **`node tools/e2e/ws-smoke.js`** | 功能测试（27 项） | **压测前后的回归**：确认压测没把状态机压坏 | 性能测试不能替代功能测试 |
| **`/proc/stat`** | Linux 内核的 CPU 累计计数器 | 算区间 CPU 占用（见 2.5） | 精确、可脚本化、无需装监控 |
| **`/proc/self/statm`** | 进程内存统计（第 2 个字段是常驻页数） | 换算 RSS（MB） | 比 `ps` 稳定，直接读内核计数 |
| **`/proc/self/fd`** | 进程打开的 fd 目录 | `ls | wc -l` 就是 fd 数 | 泄漏检测最直接的手段 |
| **`systemctl show -p LimitNOFILE`** | systemd 单元配置查询 | 确认 fd 上限（我们 65536） | 否则 1000 连接时的 `EMFILE` 会被误判成 bug |
| **`ss -lntp`** | 查看监听端口与进程 | 确认 8888/3478/443 在监听、谁在监听 | 部署后第一件事 |
| **`journalctl -u webrtc-signaling`** | 读 systemd 日志 | 看错误、看启动时加载了什么配置 | 唯一的线上"日志真相" |

> 注意 `/stats` 这种"自己给自己做指标"的做法，本质就是 Prometheus exporter 的雏形：把 JSON 换成 Prometheus 文本格式、挂到 `/metrics`，Prometheus 就能直接抓（见 3.3）。

### 3.2 为什么不用 `ab` / `wrk` / JMeter / k6 / Locust

这是面试和答辩最容易被追问的一句："你为什么不用现成工具？"先认识它们：

| 工具 | 语言/形态 | 擅长 | 为什么这次不合适 |
|---|---|---|---|
| **ab**（ApacheBench） | C，命令行 | HTTP 单接口压测，极简 | 只支持 HTTP，**不支持 WebSocket**；也无法表达"先 auth 再 join 再等 start_call"的时序 |
| **wrk / wrk2** | C + Lua 脚本 | HTTP 高并发，吞吐极高（wrk2 还能修正 coordinated omission） | 同样只做 HTTP；要测 WS 得自己写 Lua 协议栈 |
| **JMeter** | Java，GUI | 全协议、有 WebSocket Sampler 插件、报表全 | 单机开销大（GUI + JVM 就吃掉一个核），脚本是 XML 不好维护；**压测机自己会成为瓶颈** |
| **k6** | Go + JS 脚本 | 现代化、原生支持 WS、脚本好写 | 最接近的替代品；不选它主要因为要额外装 k6，且我们要复用项目里的 JWT 签名细节与协议断言 |
| **Locust** | Python + 协程 | 分布式、脚本灵活、Web UI 好看 | 同样要重写协议；Python 单进程吞吐低于 Node/V8 的事件循环 |
| **tsung** | Erlang | 老牌、支持 WS、天然分布式 | 学习成本高（Erlang 配置），改一次场景很重 |
| **artillery** | Node | 配置化、支持 WS、生态好 | 可选；但它把"延迟分布"封装得太深，我们要自定义 trace/直方图反而不方便 |

**结论（这才是要记住的判断方法）**：选压测工具看三件事——
1. **协议**：HTTP 用 wrk/ab 就够了；WebSocket、gRPC 就得 k6/Locust/自研。
2. **是否有状态**：只打一个接口 → 现成工具；要"登录→进房→配对→收推送"这种多步有依赖的流程 → 要么用工具的高级脚本能力，要么自己写。
3. **压测机够不够**：工具越重（JMeter GUI），能压的量越少。**压测机必须比被测服务强一个量级。**

本项目三条都指向"自己写"：协议是自定义 JSON、流程强有状态、还要塞 trace 和自定义直方图。用 Node + `ws` 写 700 行，比给 JMeter 写插件快，也比 wrk 写 Lua 协议栈靠谱。

### 3.3 观测类工具（这次没用，但必须知道）

| 工具 | 是什么 | 用在哪 | 为什么这次没上 |
|---|---|---|---|
| **Prometheus** | 指标采集 + 时序数据库 | 定时抓 `/metrics`，长期存储，做趋势图 | 单机演示、4 GiB 内存，先用手工 `/stats` 达到同样目的 |
| **Grafana** | 可视化看板 | 把 Prometheus 数据画成图 | 同上；本次用报告里的表格代替 |
| **node_exporter / cAdvisor** | 采集主机/容器指标 | CPU、内存、网络、fd 的长期曲线 | 同上 |
| **perf** | Linux 性能剖析（采样调用栈） | 找 CPU 热点函数（比如"日志占了 30% CPU"） | 没有 CPU 热点疑问，先用 `/proc/stat` 够用 |
| **strace / bpftrace** | 系统调用跟踪 | 看是不是卡在 `write()`/`epoll_wait()` | 侵入性大，演示环境不想引入 |
| **tcpdump / Wireshark** | 抓包 | **验证 Nagle 最直接的手段**（能看到 40 ms 的 ACK 间隔） | 这次靠应用层 trace 推出来的；有抓包会更硬 |

> 一句话：**`/stats` 解决"服务端忙不忙"，Prometheus+Grafana 解决"长期趋势和告警"，perf 解决"为什么忙"。** 三者是递进关系，不是替代关系。

### 3.4 别忘了看压测机自己

最容易被忽略的观测对象是**压测机**。

2000 连接那次，客户端的数字难看到像服务端崩了（P99 285 ms），实际是**客户端单进程 Node 已经 100% CPU**：一个事件循环要处理 2000 个 socket、每秒 8000 条探针进出。

看压测机的方法很简单：Windows 上任务管理器/`Get-Counter`，Linux 上 `top`。

**经验法则**：压测机 CPU 超过 70%，这次压测的结论就只能当"下限"用，不能当"容量上限"——你测的是压测机。正确做法是把压测客户端拆成多个进程（本工具支持 `--prefix` 分段），或者换多台机器压。

## 4. 压测要回答什么、不回答什么

| 要回答 | 不回答 |
|---|---|
| 单机能挂多少连接、多少个双人房间 | 媒体通路能跑多少路（那是带宽和 TURN 的事） |
| 连接建立/入房/消息转发的延迟分布 | 数据库能扛多少 QPS（信令不连库） |
| 规模涨上去之后，哪一类操作先变慢 | 跨机房、公网抖动下的表现 |
| 内存、文件描述符会不会线性泄漏 | 长时间（小时级）稳定性（见第 10 节） |

**信令服务和媒体是两回事**：信令只是几十字节的 JSON 转发，一条消息的 CPU 成本是微秒级；真正吃带宽的是 TURN 中继的媒体流（单路约 3 Mbps）。所以"能扛多少路通话"这个问题的答案是**带宽决定的**，不是信令决定的。压测压的是"信令会不会先撑不住"。

## 5. 怎么测的

### 5.1 不用"挂几千个空 socket"

最容易做错的一件事：开 5000 个 WebSocket 连上就完事，然后宣布"支持 5000 并发"。
那样测出来的是**操作系统的 TCP 栈**，不是业务容量——真实用户不会连上就干坐着。

`tools/load/loadtest.js` 里每个连接都完整走一遍真实业务顺序：

```
TCP+WS 握手 → auth（JWT 验签） → join_room（roomToken 验签、占座）
   → 收 start_call（服务端配对派发） → offer / answer 转发
   → 稳态：ICE 探针互发 + 每 5 秒一次 video_mute / mic_mute
   → bye 挂断 → 断开
```

这样测出来的延迟，和用户按下"加入房间"后实际等待的时间是同一件事。

### 5.2 两种模式

| 模式 | 做了什么 | 回答什么问题 |
|---|---|---|
| `--mode signaling`（主力） | 本地用 `JWT_SECRET` 签 access/room token，直连 8888 端口 | **信令服务本身**能扛多少（排除 nginx / Go / PostgreSQL 干扰） |
| `--mode fullstack` | 走真实 HTTPS API：注册 → 建房 → `POST /api/rooms/{id}/join` 换 roomToken | 整条链路能不能一起工作（规模开不大，注册有限流） |

主力用 signaling 模式，是因为要隔离变量：如果混着压，CPU 到底花在 nginx、Go 还是 C++ 上就说不清了。

### 5.3 为什么必须同时看"客户端数字"和"服务端数字"

- **客户端数字**（连接建立、auth 往返、join_room、offer→answer、ICE 往返）：包含网络 + 排队 + 服务端处理，最接近用户感受，但**也包含压测机自己的开销**。
- **服务端数字**（`/stats` 里的 `latencyUs`）：从收到消息到发出转发之间的纯内部耗时，不含网络。它能告诉你"服务端到底忙不忙"。

第 5.3 节会看到：2000 连接时客户端 P99 是 285 ms，而服务端 P95 只有 0.5 ms——**这 285 ms 里绝大部分是压测机自己排队的时间**。只看客户端数字，会得出完全错误的结论。

### 5.4 环境

| 项 | 值 |
|---|---|
| 服务端 | Ubuntu 24.04.3，4 vCPU / 4 GiB（VMware 虚机，NAT） |
| 服务端版本 | `server.cpp` 1290 行，`setThreadNum(4)`，Release 编译，`-Wall` 零告警 |
| 客户端 | Windows 11 宿主机，Node 24.15.0，单进程 |
| 网络 | 宿主机 ↔ 虚机同 NAT 网段（192.168.220.x），RTT < 1 ms |
| 服务端统计 | `/stats?token=...`，每 5 秒采样一次 |

> 同网段意味着**网络延迟几乎为零**，测出来的都是服务端和客户端的处理时间。换成公网，每条数字都要加上 20~60 ms 的 RTT——但那是网络的事，不是服务容量的事。

## 6. 结果

### 6.1 S1：连接建立随规模变化

同一套流程，只改房间数（每房 2 人）。单位 µs。

| 连接数 | 连接建立 P95 | auth P95 | join P95 | offer→answer P95 | ICE P95 | 错误数 |
|---|---|---|---|---|---|---|
| 100 | 5 000 | 1 000 | 1 000 | 2 500 | 2 500 | 0 |
| 500 | 5 000 | 5 000 | 2 500 | 2 500 | 5 000 | 0 |
| 1 000 | 10 000 | 5 000 | 5 000 | 5 000 | 25 000 | 0 |
| 2 000 | 25 000 | 5 000 | 5 000 | 10 000 | 50 000 | 0 |

**服务端内部耗时（同一批运行，`/stats` 累计值）**：

| 连接数 | 转发 P95 | 入房 P95 | RSS | 文件描述符 |
|---|---|---|---|---|
| 100 | 250 | 500 | 24.9 MB | 122 |
| 500 | 500 | 500 | 26.4 MB | 522 |
| 1 000 | 500 | 500 | 28.3 MB | 1 022 |
| 2 000 | 500 | 500 | 32.6 MB | 2 022 |

**两个关键读数**：

1. **连接数涨 20 倍，服务端转发 P95 只从 250 µs 涨到 500 µs**（还没到下一个桶），入房 P95 一直是 500 µs。说明服务端处理能力远未饱和。
2. **文件描述符 = 连接数 + 22**，是严格线性的、没有泄漏。每个 WebSocket 占 1 个 fd，这是必然的（Linux 上就是 socket）。
3. **内存**：24.9 MB → 32.6 MB，增量 ≈ 4 KB/连接。2000 连接才多占 8 MB，**内存根本不是问题**。

### 6.2 S2：同参数连跑两次，验证"数字可信"

场景：200 房间 / 400 连接 / 爬坡 20 s / 稳态 60 s，跑两遍。服务端指标在每轮开始前用 `?reset=1` 清零，所以是"单轮窗口"。

| 指标 | 第 1 轮 | 第 2 轮 | 差异 |
|---|---|---|---|
| 转发 P50 | 100 µs | 100 µs | 0% |
| 转发 P95 | 250 µs | 250 µs | 0% |
| 转发 P99 | 1 000 µs | 1 000 µs | 0% |
| 入房 P95 | 500 µs | 500 µs | 0% |
| 转发 MAX | 6 385 µs | 2 590 µs | — （MAX 是单次抖动，不看差值） |
| 客户端 ICE P95 | 10 000 µs | 10 000 µs | 0% |
| 客户端错误数 | 0 | 0 | — |

P50/P95/P99 **三轮完全一致**，说明测量方法是可重复的，不是"跑一次碰巧好看"。这就是为什么要跑两遍——**只跑一次得到的数字，你不知道它是规律还是运气**。

> MAX 不一致是正常的：MAX 记录单次最坏值，一次 GC 或一次调度抖动就能改变它。判断稳定性看 P95/P99，不要看 MAX。

### 6.3 S3：房间数涨 10 倍，谁先变慢

场景：1000 房间 / 2000 连接 / 爬坡 60 s / 稳态 30 s。对比对象是 S2 的 200 房间。

> 本节及 6.1~6.4 的数字都是**阶段二优化之前**的基线；优化之后的重跑结果见 6.5。

| 指标 | 200 房间（S2） | 1000 房间（S3） | 变化 |
|---|---|---|---|
| 服务端入房 P50 | 250 µs | 250 µs | 不变 |
| 服务端入房 P95 | 500 µs | **1 000 µs** | 翻倍 |
| 服务端入房 P99 | 1 000 µs | **2 500 µs** | 2.5 倍 |
| 服务端转发 P95 | 250 µs | **500 µs** | 翻倍 |
| 服务端转发 P99 | 1 000 µs | **2 500 µs** | 2.5 倍 |
| 服务端 CPU | 4.6% | **15.3%** | 3.3 倍 |

**这是全篇最有信息量的一张表**：

- 房间数 ×5、连接数 ×5，**延迟只涨了 2 倍左右，而且是"桶级别"的翻倍**（500 → 1000 µs）。
- 说明存在随规模上升的成本，但**上升得比线性慢得多**，不是"O(n²) 卡死"。
- 这部分成本来自现有实现的两个设计：`g_rooms` 是**单个全局 map + 一把全局锁**，且找房间、找对端都要**遍历**。房间少的时候无所谓，房间上千后开始有可测量的代价——但绝对值仍只有 1 ms。

**结论**：现实现能撑到 1000 房间，但如果你要往"万房间"走，这两个点必须先改（见第 8 节）。

**怎么读这两张表（这部分比数字重要）**

1. **收益全部落在"转发"的长尾上，中位数一点没动。** P50 一直是 100 µs（就是我们直方图的最小桶），说明"空闲时转发一条消息"本来就快到无法再快；被优化掉的是**排队等待**——房间数越多，原来要遍历的房间就越多，排队就越久，于是 P95/P99 先变差。这也解释了为什么"P50 不变 + P99 大幅下降"是一个**修复了争用**的典型特征（对比 2.6 节里"P50 不变 + P95 翻倍 = 长尾劣化"）。
2. **转发 P99 从 2.5 ms 掉到 0.25 ms，是 `conn → roomId` 索引的直接结果。** 原来转发一条消息要先拿到 `g_rooms` 锁、把 1000 个房间的成员列表全扫一遍；现在是一次哈希查找，锁占用时间从"和房间数成正比"变成"常数"。
3. **入房 P50 反而变差了 0.25 ms，这是真事，不是噪声。** 因为入房现在除了房间锁，还要额外拿一次身份分片锁把 `roomId` 写进索引里。绝对值 0.25 ms，而 P99 同时从 2.5 ms 降到 1.0 ms——**用中位数换长尾，在这种场景是划算的**（一次通话只入房一次，但要转发上万条消息）。这条也写进了提交信息，避免以后有人看到"变慢"以为哪里写错了。
4. **CPU 没有明显下降，这是合理的。** 优化掉的是"等锁/等遍历"，不是"算"。原来那些时间片是**空转在自旋和调度上**，现在只是少了等待；真正占 CPU 的 memcpy、JSON 解析、日志一条没少。日志降档（`LOG_PAYLOAD` 默认关）在 2000 连接这个量级也没测出可见降幅——噪声大于收益，如实记下。
5. **身份表分 16 片这一步，实测没有可测量差异。** 说明这层锁在 2000 连接 / 约 1.2 万条消息每秒下**还不是瓶颈**。保留它的原因是给更多核、更高消息率留余量，代价是代码从 1 个 map 变成 16 个分片。如果要追求最小改动，这一步可以回退——报告里如实标注"未验证收益"，比声称"优化了"更可信。
6. **客户端侧 ICE P99 285 ms 依旧存在**，跟优化前一样。那是压测客户端单进程的限制（见 7.3），不是服务端；判断服务端有没有变好，只能看 6.5 这两张表的"服务端"列。

> 两个新增指标也一并上线：`errors.rate_limited`（单连接 > 60 条/秒，突发 120）与 `errors.slow_client`（对端未读缓冲 > 256 KiB）。优化后的所有压测里这两个值都是 0——说明限流阈值没有误伤正常客户端。

## 7. 三个发现（比数字更值钱的部分）

### 7.1 发现一：一次 offer 转发莫名多出 43 ms，罪魁是 Nagle

**现象**：小规模试跑（2 个房间）时，`offer→answer` 稳定落在 25~50 ms 的桶里，而 ICE 往返只有 1 ms。同一个连接、同一个服务端，为什么一个 1 ms、一个 43 ms？

**定位过程**：
1. 先怀疑 perfect negotiation 卡住/丢轨道 → 排除（状态都是 `stable`）；
2. 再怀疑服务端锁 → 服务端 `/stats` 显示转发 P95 只有 250 µs，排除；
3. 给压测脚本加 `--trace`，在 offer 里塞一个 `Date.now()`，对端收到时算差值：

```
[trace LT00000#0] offer sent
[trace LT00000#1] offer recv, 发出函数 43ms 前     ← 延迟发生在路上
[trace LT00000#1] answer sent
[trace LT00000#0] answer recv +44ms               ← 回程几乎是 0
```

延迟**单向**发生在"发起方 → 服务端 → 接收方"这条路上，回程正常。

**机理**：这是经典的 **Nagle 算法 + 延迟 ACK 撞车**。
服务端刚给客户端写完 `start_call`（小包），紧接着要转发 `offer`（也是小包）。Nagle 规定"上一个包没被 ACK 之前，不能再发小包"，于是 `offer` 被压住；而对端因为"暂时没有数据要回"，把 ACK 延迟了最多 40 ms。两个机制一撞，就是 40 ms 级别的固定延迟。

**为什么 ICE 探针不出来**：ICE 每 250 ms 才发一条，发的时候连接一定是"空闲已 ACK"状态，Nagle 不生效。**只有"连续两条小消息背靠背"才会踩坑**——而信令恰恰全是这种模式。

**修复**：`server.cpp` 的 `onConnection` 里加一行：

```cpp
conn->setTcpNoDelay(true);   // 关掉 Nagle
```

**效果**：

| | 修复前 | 修复后 |
|---|---|---|
| offer→answer P50 | 50 000 µs | 1 000 µs |
| offer→answer P95 | 55 000 µs | 2 500 µs |

**这条要记住**：看到"40 ms 整数倍"的延迟、又找不到代码逻辑问题，先怀疑 Nagle + 延迟 ACK。而且它只在**小包背靠背**的场景出现，所以"平时都是 1 ms"和"偶尔 43 ms"完全可以共存。

### 7.2 发现二：`/stats` 不清零，两次压测"看起来一样"是假的

第一版 `/stats` 的直方图是进程启动以来的**累计值**。所以拿 200 房间跑两遍，P95 都是一模一样的 500 µs——
**不是因为它稳定，而是因为第二遍的样本里掺着第一遍的历史数据**，任何波动都被平均掉了。

这是压测里很隐蔽的一个坑：**你以为在验证稳定性，其实在验证平均值**。

**修复**：`/stats?reset=1`，在鉴权通过后把计数器和直方图清零，压测脚本每轮开始前先调一次。加完之后再对比两轮，P50/P95/P99 依然一致——**这次的一致才是真的**（见 6.2）。

顺带一个设计原则：这种"重置/危险操作"必须挂在**已经鉴权的路径**后面，`/stats` 本身不带 token 是 403，所以谁都不能清别人的窗口。

### 7.3 发现三：先到瓶颈的是压测客户端，不是服务端

2000 连接时，客户端视角的数字很难看：

```
ICE 往返  P50 10 000 µs   P95 50 000 µs   P99 285 000 µs
```

如果只看这张表，结论会是"服务端在 2000 连接时已经扛不住了"。但同一时刻服务端 `/stats` 是：

```
转发 P50 100 µs   P95 500 µs   P99 2 500 µs   CPU 15%
```

**两个数字差了 100 倍，因为 285 ms 里绝大部分是压测机自己排队的时间**：一个 Node 进程，2000 个 socket，每秒 8000 条探针进、8000 条出，单线程事件循环处理不过来，消息在客户端自己的队列里等着。

**这条教训有两面**：
- 压测机的处理能力必须**远大于**被测服务，否则测的是压测机；
- 客户端数字只能用来回答"用户感受"，**容量结论必须用服务端数字**，或者用 CPU/内存这类客观量。

正确的做法（下一步）：把压测客户端按 `--prefix` 拆成多进程，让客户端的总算力跟得上，再看 2000/4000 连接时服务端的真实拐点。

## 8. 瓶颈在哪：设计假设 vs 实测

评审阶段列过"6 把全局锁、线性扫描房间、每条消息打日志"这几条隐患。现在用数据对照一下：

| 设计问题 | 实测表现 | 判断 | 阶段二处理 |
|---|---|---|---|
| 7 个全局 map + 7 把互斥锁 | 1000→2000 连接，转发 P95 250→500 µs | **有代价但可控**，还没撞上锁竞争 | 身份表分 16 片（实测无可测收益，属留余量）；转发路径改为锁外发送 |
| 找房间/找对端要遍历 | 房间 200→1000，入房 P95 500→1000 µs | **开始有成本**，万房间前要加索引 | **已加 `conn → roomId` 索引**，转发 P99 2.5 ms→0.25 ms（见 6.5） |
| 每条消息 `LOG_INFO` 打全量 payload | CPU 15% 里有一部分是日志 | 未单独量化；**压测时日志是纯噪声** | 已降档：默认只记类型+长度，`LOG_PAYLOAD=1` 才打全量 |
| `conn->send()` 无背压 | 未测（需要慢客户端才能触发） | **仍待验证**：真实用户网络差时会在这里堆积内存 | 已加判定（缓冲 > 256 KiB 断开并计 `slow_client`），**但还没用慢客户端实测** |
| 单连接可以无限刷消息 | 未测 | 一条连接就能把 CPU 打到饱 | 已加令牌桶（60 条/秒、突发 120），超限断连 |
| `setThreadNum(4)` 在 2 核机器上 | 虚机给了 4 核，未测 2 核 | 云上用 2 vCPU 时要复测 | 未处理 |
| muduo 是瓶颈 | 显式排除：0.61 核跑 12k msg/s | **muduo 不是瓶颈**，应用层才是 | — |

一句话：**优化前瓶颈顺序是 ①客户端/带宽 ②线性扫描 ③日志 I/O；现在 ②③ 已经解决，瓶颈回到 ①客户端/带宽**——也就是说，这台虚机上的信令服务已经比"用来压它的单进程客户端"更能扛。

## 9. 容量结论

基于实测（4 核虚机、同网段、`-Wall` Release 构建）：

| 维度 | 实测值（优化前） | 优化后 | 推算 |
|---|---|---|---|
| 连接数 | 2000 连接时 CPU 15%、转发 P95 0.5 ms | 转发 P95 **0.1 ms**、CPU 7% | 单机 **2000~4000 连接** 是安全区 |
| 房间数 | 1000 房间时入房 P95 1 ms | 入房 P99 2.5 ms→**1 ms** | 已有索引，万房间不再是硬墙 |
| 消息吞吐 | 约 12 000 条/秒（收发合计）@ 0.61 核 | 同量级，延迟腰斩 | 单核约 18 000 条/秒 |
| 内存 | 4 KB/连接，2000 连接 32.6 MB | 31.9 MB | 内存不是约束，1 万连接也就 70 MB 左右 |
| 文件描述符 | 连接数 + 22，线性无泄漏 | 同 | 注意 `LimitNOFILE`（当前 65536，够用） |


**换算成"多少路通话"**：一个双人房间 = 2 个连接，所以 2000 连接 ≈ **1000 路同时在线通话**。但请注意：

- 这是**信令**能支撑的通话数，不含媒体；
- 媒体走 TURN 中继时，单路约 3 Mbps。**200 Mbps 带宽只够 60~70 路中继**——所以真正限制"多少路能打通"的是带宽，不是这台服务器；
- 同网段 P2P 直连时媒体不过服务器，带宽不占，信令才是瓶颈。

**给答辩的一句话**：
> 信令服务单机可支撑 1000 路并发通话（2000 连接），P95 转发延迟 0.1 ms、CPU 7%；实际"多少路能打通"受限于 TURN 中继带宽约 3 Mbps/路。

## 10. 没测的、以及已知偏差

**没测**：
1. **长稳 S4**（200 房间跑 1 小时）——需要一小时独占机器，还没排期。这一项主要看 `rssMb` 和 `fds` 会不会缓慢上涨。
2. **慢客户端背压**——判定逻辑已经实现（对端输出缓冲 > 256 KiB 就断开并计 `slow_client`），但**还没有一个"故意不读数据"的客户端去真的触发它**，所以只能说"有防护"，不能说"验证过防护有效"。
3. **公网延迟下的表现**——同网段测不出 RTT 影响；公网场景要加上 20~60 ms 基线。
4. **媒体/带宽**——本次完全没压媒体，TURN 的容量结论来自带宽算术，不是实测。

**已知偏差**：
1. S1 那批的服务端数据是**累计值**（当时还没做 `?reset=1`），所以"P95 稳定"这个结论偏保守——累计值天然更平滑。S2/S3 都是单轮窗口。
2. 压测客户端是单进程，**2000 连接时客户端已经成为限制因素**（见 7.3），所以 2000 连接的数字是"下限"而不是"极限"。
3. 虚机是 NAT 网络，跟真机网卡中断处理有差异，绝对数字可能有 10~20% 偏差。
4. **CPU 对比不可全信**：优化前那次 S2/S3 的窗口里，恰好在跑 `unattended-upgrade`（占满一个核），所以 15.3% 里有一部分是它。优化后重跑时已经把后台任务停掉了。真正可比的是**同一个工具、同一组参数下的延迟分位**（6.5 节），CPU 只作参考。
5. 6.5 节优化后的数据里，S2 跑了 3 轮（其中 2 轮窗口不干净），表里取的是干净窗口那一轮；S3 跑了 2 轮，两轮 P95/P99 一致。

## 11. 自己动手压一次（手把手）

> 这一节是可以照着敲的。假设：服务端已按 `deploy/install.sh` 部署在 `192.168.220.128`，压测机是 Windows 宿主机（Node ≥ 18）。

### 11.1 第一步：拿到两个密钥

```bash
# 在虚机上
sudo grep -E '^(JWT_SECRET|STATS_TOKEN)=' /opt/webrtc/signaling.env
```

- `JWT_SECRET`：signaling 模式要自己签 access/room token（绕过 Go 认证服务），必须和服务端一致；
- `STATS_TOKEN`：读 `/stats` 用。**没有它也能压**，只是看不到服务端内部数字（那就只剩客户端数字，结论可信度会降一档）。

两个都是**本机环境密钥**，别提交进仓库（`signaling.env` 已在 `.gitignore` 里）。

### 11.2 第二步：2 个房间跑通（永远先跑这一步）

```bash
node tools/load/loadtest.js --host 192.168.220.128 --mode signaling \
  --secret "<JWT_SECRET>" --stats-token "<STATS_TOKEN>" \
  --rooms 2 --ramp-up 1 --duration 5 --reset
```

真实输出（本次实测，`--rooms 2` 就是 2 房间 4 连接）：

```
==> 目标=ws://192.168.220.128:8888/ws 房间=2 连接=4
    爬坡=1s 稳态=5s ICE=4/秒/连接
    已重置服务端计数窗口（只统计本轮）

===== 客户端视角 =====
指标           样本数     P50      P95      P99      MAX   (单位 µs)
连接建立               4     5000    10000    10000     6000
auth 往返            4     1000     2500     2500     2000
join_room          4     1000     1000     1000     1000
offer→answer       2     1000     2500     2500     2000
ICE 往返            84     1000     2500     5000     4000

发出：{"auth":4,"join_room":4,"offer":2,"answer":2,"ice":88,"video_mute":6,"mic_mute":6,"bye":4}
收到：{"auth_ok":4,"joined":4,"start_call":4,"offer":2,"answer":2,"ice":88,"video_mute":6,"mic_mute":6,"bye_ack":4}
错误：{}
结论：无错误

===== 服务端 /stats（结束时快照）=====
连接数：{"authed":0,"unauthenticated":0,"ws":0}
房间数：{"full":0,"members":0,"total":0}
消息数：{"answer":2,"auth":4,"bye":4,"ice":88,"join_room":4,"list_rooms":0,"mic_mute":6,"offer":2,"other":0,"video_mute":6}
错误数：{"auth_fail":0,"auth_timeout":0,"bad_json":0,"invalid_room_token":0,"room_full":0}
自测延迟：{"forward":{"max":372,"p50":100,"p95":250,"p99":500,"samples":104},
          "join_room":{"max":1132,"p50":250,"p95":500,"p99":500,"samples":4}}
资源：{"fds":22,"rssMb":32.2}
```

**怎么读这段输出（新手最容易看错的三处）**：

| 你看到 | 意思 | 要检查什么 |
|---|---|---|
| `发出` 和 `收到` 的数量**对得上** | 每个 `auth` 有 `auth_ok`、每个 `offer` 有对端收到、每个 `bye` 有 `bye_ack` | 数量不对 = 有消息丢了或被丢弃，先去查协议而不是加量 |
| `错误：{}` | 一条错误都没发生 | 只要有内容就先停，10 个连接就出错是 bug 不是容量 |
| `连接数`/`房间数` 最后都是 **0** | 收尾时连接都正常断开了、空房间被回收了 | **如果不为 0，说明有连接/房间泄漏**，这是每轮压测必查的一项 |
| `samples` 很小（如 `join_room: 4`） | 样本数 = 发生次数。入房只发生 4 次，所以分位数没统计意义 | 分位数要样本 ≥ 100 才可信；小样本只看 MAX 有没有离谱 |
| `ICE 往返 samples: 84` | 稳态期间每连接每秒 4 条探针 × 4 连接 × 5 秒 ≈ 80 | 数量级对不对是判断"压测真的在跑"的快速办法 |

> 为什么 `连接建立 P95 = 10 000 µs` 比 `join_room = 1 000 µs` 大一个数量级？因为前者包含 TCP 三次握手 + WS 握手 + 一次 auth 往返，而后者只是"已经连上的连接再发一条消息"。**别拿不同指标互相比较**，只有同一指标在不同规模下比较才有意义。

### 11.3 第三步：逐档加量，每一档都先看错误率

```bash
# 100 连接（50 房间）
node tools/load/loadtest.js --host 192.168.220.128 --mode signaling \
  --secret "<JWT_SECRET>" --stats-token "<STATS_TOKEN>" \
  --rooms 50 --ramp-up 5 --duration 30 --reset

# 500 连接（250 房间）
... --rooms 250 --ramp-up 10 --duration 30 --reset
```

每档停下来看两件事：**错误数必须还是 0**、**服务端 fd ≈ 连接数 + 22**。这两条不过，就不要再加量——那不是容量问题。

### 11.4 第四步：跑"稳态 + 两遍"，这样数字才可信

```bash
# 第一遍
node tools/load/loadtest.js --host 192.168.220.128 --mode signaling \
  --secret "<JWT_SECRET>" --stats-token "<STATS_TOKEN>" \
  --rooms 200 --ramp-up 20 --duration 60 --reset --out .tmp/load/s2-1.json

# 第二遍（参数完全一样）
... --out .tmp/load/s2-2.json
```

对比两份 JSON 里的 `P50/P95/P99`：**差异 < 10% 才算"这个数字可信"**。差异大说明有外部因素（机器在跑别的、客户端到瓶颈了、忘了 `--reset`）。

### 11.5 第五步：大规模（跑到客户端先撑不住为止）

```bash
# 1000 房间 / 2000 连接
node tools/load/loadtest.js ... --rooms 1000 --ramp-up 60 --duration 30 --reset
```

到这一步要开始盯**压测机自己**的 CPU（见 3.4）。客户端 CPU 打满时，客户端数字只能当下限用。

### 11.6 收尾（每次都做）

```bash
# 虚机上：清掉残留房间与计数
sudo systemctl restart webrtc-signaling

# 宿主机：功能回归，确认压测没把状态机压坏
node tools/e2e/ws-smoke.js 192.168.220.128 8888
```

### 11.7 报错对照表

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 全是 `invalid_token` | `--secret` 与服务端 `JWT_SECRET` 不一致 | 重新读 `signaling.env`；注意别把 `\r` 或引号带进去 |
| `invalid_room_token` | 签名对了但 `typ` 不对（用 access token 当进房凭证） | 工具会自动签两种，检查服务端是不是老版本 |
| fullstack 模式注册 429 | 注册限流（5 次/分、突发 3） | 用 `--accounts` 少开几个，或直接用 signaling 模式 |
| `ECONNREFUSED` / 连接超时 | 服务没起 / 端口不对 / 防火墙 | `systemctl status webrtc-signaling`、`ss -lntp \| grep 8888` |
| 压完 `/stats` 里仍有房间 | `bye` 没发完就断连（或客户端被 Ctrl+C） | `systemctl restart` 清掉；正常收尾应该是 0 |
| 客户端 P99 很离谱但服务端很小 | 压测机到瓶颈了 | 看客户端 CPU；拆多进程（`--prefix`）或换机器 |
| 延迟是 40 ms 的整数倍 | Nagle + 延迟 ACK（见 7.1） | 确认服务端有 `setTcpNoDelay(true)` |

### 11.8 全链路的一种跑法

```bash
NODE_TLS_REJECT_UNAUTHORIZED=0 node tools/load/loadtest.js --mode fullstack \
  --host 192.168.220.128 --api-host 192.168.220.128 --api-port 443 \
  --accounts 2 --rooms 5 --duration 10
```

这条走的是真实链路（nginx → Go → PostgreSQL → roomToken → wss），规模开不大，用来确认"整条链路一起工作没问题"。`NODE_TLS_REJECT_UNAUTHORIZED=0` 是因为自签证书。

工具参数、多进程分段与 `--merge` 见 `tools/load/README.md`。
